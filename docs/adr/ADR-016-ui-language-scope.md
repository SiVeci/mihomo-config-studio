# ADR-016：界面语言范围——1.0 简体中文界面 + 完整英文 i18n 资源结构

- 状态：Accepted
- 日期：2026-08-13
- 来源：PRD §19-4（开发前置决策第 4 项）

## 背景

PRD §19 把「是否在 1.0 提供英文界面，或只完成英文资源结构」列为须在 M0 结束前
冻结的前置决策，默认建议是「先支持简体中文界面，同时完整建立英文 i18n 结构」。
这项取值已于 2026-08-10 定案（执行计划「已确认的决策」Q3），本 ADR 不重新讨论
选型，只记录决策对实现的硬约束——这是本 ADR 存在的主要理由：语言范围本身
是产品决策，但"资源结构必须从第一行代码起就齐全"是一条会反向影响所有
UI 代码写法的架构约束，值得单独记录而不是只在 PRD 里提一句。

## 决策

1. **v1.0 界面只做简体中文**：不在 1.0 交付英文（或其他语言）界面翻译文案。
2. **英文 i18n 资源结构必须从第一行代码起完整建立**：所有用户可见文本一律走
   i18n key，不写字面量字符串；英文资源文件与中文同步维护——键必须齐全，
   值可以是占位翻译（例如直接复用中文或英文机器翻译），但不允许键缺失。

## 对实现的硬约束

这条决策直接约束所有产出用户可见文本的代码：

- **禁止字面量**：组件代码里不出现直接书写的中文（或任何语言）用户可见字符串，
  一律通过 i18n key 查表。这条约束已经写进本仓库的工程约束（历次执行计划均
  重申「用户可见文本一律 i18n key，不写字面量」），本 ADR 是其正式来源。
- **中英资源文件同步新增**：新增或修改一个 i18n key 时，中文资源文件与英文
  资源文件必须同时改动——英文值允许是占位翻译，但不允许该 key 只存在于
  中文资源文件里。校验/CI 层面的强制检查（例如"两份资源文件的 key 集合必须
  相等"）留给实际引入 `apps/web` 与 i18n 库时一并实现，本片只冻结决策本身，
  不实现校验工具。
- **错误码 / 校验失败信息同样适用**：`packages/schema-core` 的校验失败信息
  目前只暴露 `code` + `path`（NFR-SEC-03 已有此约束），实际渲染成用户可见文本时
  同样要走 i18n key，`code` 到文案的映射表要中英文同步维护。

### 为什么现在就要付出这个成本

若 1.0 只按中文写字面量、事后再补 i18n，代价是把已经写好的每一处用户可见文本
重新过一遍、抽 key、再补英文——工作量不比一开始就走 i18n key 小，还要冒改漏的
风险。反过来，从第一行代码开始就走 i18n key，中文 UI 的开发成本几乎不变（多一次
查表调用），但换来 1.0 之后开英文界面**不需要改任何组件代码**，只需要把英文资源
文件的占位翻译换成真实翻译。这是本 ADR 存在的核心理由：把一次性的架构决策
成本换成后续版本的零组件改动成本。

## 结果

- PRD §19 第 4 项：已落文，无待办。
- 本约束对当前已完成的 `packages/**` 代码**无追溯要求**：v0.1.0 范围内的
  `config-model`、`graph`、`schema-registry` 等包不含面向最终用户的界面文本
  （校验失败只暴露 `code` + `path`，未做文案映射），本 ADR 约束的是**引入
  `apps/web` 起才会出现的组件代码**，不需要回头改造已有代码。
- 不需要新增 `docs/upstream-divergences.md` 条目：这不是 PRD 与上游行为的冲突，
  是 PRD 明确列为待冻结的前置决策，按其自身默认建议定案。
