# v0.2.0 性能基线：1 MB 语料导入（NFR-PERF-02）

覆盖切片 #16。记录 1 MB YAML 语料经真实导入路径（`MihomoYamlDocument.parse()` +
`runPipeline()`，与 `apps/web/src/worker/protocol.ts` 的 `handleParse` 完全一致）的
耗时基线，退出条件是总计 < 2 秒。

**口径限定**：数字来自本机开发环境，不是 CI 标准环境、也不是专门在最低支持版本
Node 20.11 上采样的结果（见下文"已知缺口"）。退出条件只要求"< 2 秒"，不要求锁定
具体机器，这里只记录一次可复现的基线，不做跨机器/跨版本对照。

## 测试环境

| 项目       | 值                                                                                  |
| ---------- | ----------------------------------------------------------------------------------- |
| CPU        | Intel(R) Core(TM) i5-14600KF（20 逻辑核心）                                         |
| 内存       | 31.8 GB                                                                             |
| 操作系统   | Windows 10.0.26200（win32/x64）                                                     |
| Node.js    | v24.12.0                                                                            |
| 语料生成器 | `packages/test-fixtures/src/generate-large.ts`，固定种子 `20260210`                 |
| 语料大小   | 1,048,669 字节（约 1.00 MiB），36,963 行                                            |
| 基准工具   | `vitest bench`（`packages/validator/src/bench/import.bench.ts`），每项 `time: 3000` |
| 采样次数   | 5 次独立进程调用（`pnpm vitest bench --run` 各跑一次），取每次报告 mean 的中位数    |

## 结果

| 阶段                                    | 5 次采样的 mean（ms）                      | 中位数（ms） | RME 范围      |
| --------------------------------------- | ------------------------------------------ | ------------ | ------------- |
| 解析（`MihomoYamlDocument.parse`）      | 443.52 / 426.88 / 245.86 / 435.69 / 446.08 | **435.69**   | 16.50%–29.38% |
| 首轮校验（`runPipeline`，已解析文档）   | 全部 ≈ 0.0001                              | **≈ 0.0001** | 0.48%–0.95%   |
| 总计（解析 + 首轮校验，独立测量非相加） | 571.81 / 566.65 / 580.57 / 595.66 / 584.28 | **580.57**   | 1.31%–5.09%   |

**退出条件**：总计中位数 **580.57ms**，远低于 2000ms 阈值，约 **3.4 倍**余量。

## 复现方法

```bash
pnpm vitest bench --run packages/validator/src/bench/import.bench.ts
```

语料由固定种子生成，跨进程调用逐字节相同。三个 bench 相互独立：`解析`与`总计`各自
调用一次全新的 `MihomoYamlDocument.parse()`（不复用彼此的解析结果）；`首轮校验`用
另一份预先解析好、只解析一次的文档，隔离出不含解析开销的纯校验耗时——因此"总计"
不等于"解析" + "首轮校验"两行相加，是第三次独立测量。

## 已知缺口 / 口径说明

- **首轮校验耗时接近零，不代表校验本身廉价**——v0.2.0 的校验流水线只有 `syntax`
  阶段真实产出（`schemaStage` 目前恒返回空数组，`packages/validator/src/pipeline.ts`
  的 `DEFAULT_STAGES` 注释已写明"No module is resolved into this stage yet"）。一旦
  Schema 驱动校验落地（v0.3.0+），这个数字会显著上升，需要重新采样，届时"首轮校验"
  这一行才有实际参考价值。
- **CI 只记录不阻断**（`.github/workflows/ci.yml` 的 `perf-baseline` job，
  `continue-on-error: true`）：CI runner（GitHub `ubuntu-latest`，Node 20）性能特征
  与本机不同，共享 runner 的抖动本身就大，这个阶段设阻断线只会制造假警报——版本
  文档已把阻断阈值明确留到 v0.9.0。CI 步骤的数字只在 Actions 日志里可见，不回填本
  文档、不做跨环境比较。
- **未专门在最低支持版本 Node 20.11.0 上采样**——`engines` 字段只保证兼容性；给定
  上面 3.4 倍的现有余量，判断没有必要为此单独置备一套环境。
- **本机、非独占测试环境**：采样期间未特别隔离后台进程。5 次采样中"解析"一项的
  RME 在 16.50%–29.38% 之间（`vitest bench` 自带报告），其中第 4 次采样明显偏快
  （245.86ms，其余四次在 427–446ms 区间），推测是一次 JIT/系统调度层面的异常值；
  中位数对单点异常不敏感，这正是选中位数而非均值的原因。"总计"因每次运行都做了
  完整的解析+校验两步，相对误差反而更小（1.31%–5.09%）。
