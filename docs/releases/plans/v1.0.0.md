## 工程约束（实现时必须遵守，逐片适用）

1. Node **≥ 22.18**（ADR-030）、pnpm 10。每片验收都是
   `pnpm run check`（typecheck + lint + test）**和** `pnpm run format:check`
   ——后者 CI 单独跑，最容易漏。
2. 覆盖率阈值在 `vitest.config.ts` 强制：lines/functions/statements **85**、
   branches **80**。**不得放宽任何一项**，也不得往 `coverage.exclude` 里加新条目
   来绕开（现有 4 条排除项各自带着写明理由的注释，新增必须同等对待）。
3. 追踪表口径：标 **Done** 必须能指向具体测试文件；否则记 **Partial** 并写明缺口。
   本版本有三条明确不会转 Done 的行（§13.5 第五条、E2E Android 线、NFR-PERF-01
   的真机口径），**不得为了让 1.0 好看而改写它们**。
4. `packages/**` 禁止 `node:fs`（ESLint 强制）与任何网络调用
   （`no-network-egress` job 强制，白名单只有 `schema-registry/src/updater.ts` 一条）。
5. 工作区内部包直接导出 TypeScript 源码（ADR-007）；内部相对导入用字面 `.ts`/`.js`
   扩展名（ADR-035）。
6. 用户可见文本一律 i18n key，中英资源文件同步新增（ADR-016）。#4 新增的「关于」页
   是本版本唯一会新增 i18n key 的切片，必须同时改 `zh-CN.json` 与 `en.json`。
7. 错误与日志消息不得包含配置值（NFR-SEC-03）；`apps/web/src` 与 `packages/**` 里
   不得出现绕过 `@mcs/logging` 的直接 `console.*` 调用（`log-redaction` job 强制）。
8. `packages/test-fixtures/fixtures/**` 是字节敏感的 golden 文件：**不格式化、
   不「顺手整理」**。#3 新增的语料若落在该目录，必须同样受此约束。
9. 新增架构决策写新 ADR，不改已 Accepted 的。
10. PRD 与上游实际行为冲突时以上游为准，记入 `docs/upstream-divergences.md`，
    不得静默改需求。
11. **本版本不加任何新功能**（版本文档 Out of scope 明文）。#2 是缺陷修复，
    #4 是版本文档 §3 明文要求的声明载体，均不属于新功能。任何执行中冒出来的
    「顺手加一个小功能」诉求一律记入 `docs/roadmap-1.x.md`（#9），不进本版本。

### #3 §14.1 指标 5：1 MB 导入语料集与 ≥99% 成功率 CI 阻断（ADR-037）

**目标**：版本文档 §14.1 第五项指标写的是「1 MB 文件导入成功率 ≥ 99%
（合法测试语料）」，当前仓库只有**一个**确定性 1 MB 语料
（`generateLargeCorpus`，固定种子），既不是语料**集**，也没有任何"成功率"
口径。本片把这条指标变成一个可被 CI 回答的数字。

**覆盖**：§14.1 质量指标第 5 项；NFR-PERF-02 的语料侧扩面。

**依赖**：#0。

**涉及文件**

  **一组**语料的入口（不改既有 `generateLargeCorpus`/`generateScaleCorpus`
  的签名与输出字节——它们是既有基准的输入，改了就破坏 v0.2.0/v0.4.0 的可比性）
- 新建 `packages/validator/src/import-success-rate.test.ts`
- 新建 `docs/adr/ADR-037-import-corpus-and-success-rate.md`
- 修改 `docs/adr/README.md`

**实现要点**

- **ADR-037 要定的是口径，不是代码**，三个问题各给一个明确答案：
  1. **"合法测试语料"是什么**：由本仓库确定性生成、形态覆盖已建模的十个 P0
     模块 + 未知字段 + 注释 + 锚点 + 合并键的样本；**不包含**故意构造的
     非法样本（那是 `invalid.yaml` 的职责）。指标问的是"合法输入能不能导入
     成功"，把非法样本混进分母会让这个数字失去意义。
  2. **"导入成功"是什么**：`MihomoYamlDocument.parse()` 无 syntax issue，
     且 `runPipeline()` 产出的 issue 里**没有 blocking 项**——与
     `apps/web/src/worker/protocol.ts` 的 `handleParse` 走同一条真实路径，
     不另起一套判定。
  3. **样本量与 ≥99% 的关系**：样本数必须让"99%"有意义。**N = 100** 时
     一条失败即 99%，正好卡在阈值上——ADR 必须明确写出这个脆弱点，并给出
     选择（要么提高 N，要么把判据写成"零失败"）。**不要含糊过去**。
- 语料生成必须**确定性**（固定种子，`generate-large.test.ts` 既有的
  「同种子逐字节相同」断言要扩到新入口），否则 CI 上是随机抽样，
  失败无法复现。
- 运行时间是真实约束：100 个 1 MB 语料 × (parse + runPipeline) 在本机
  已知约 580ms/个，串行约 1 分钟。**先实测，再决定这条测试是进
  `pnpm run test` 还是像 bench 一样单独一步**；进不了默认套件就在
  `ci.yml` 加一个命名步骤（沿用 v0.9.0 #19「阻断项用命名步骤而非新 job」
  的先例）。
- 语料**不落盘**进 `packages/test-fixtures/fixtures/` 下的 golden 目录
