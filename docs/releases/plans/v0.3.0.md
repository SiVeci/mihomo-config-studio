## 先决项判定

版本文档列三项。逐条核对**代码**而非文档声明。

### 1. `inferControl` 补齐 `oneOf` / `anyOf` 分支 —— 未满足，本版本自解 → #0 / #1

核对 [`packages/schema-core/src/form-plan.ts:253-282`](../../../packages/schema-core/src/form-plan.ts)：
`inferControl` 依次判断 `enum` / `boolean` / `integer` / `number` / `array` / `object` /
`string`，**没有任何 `oneOf` / `anyOf` 分支**，判别式联合走到最后 `return 'unknown'`。
`planField`（同文件 232 行）也只在 `control === 'object'` 时递归规划子字段，联合分支的
属性根本不会被规划。

`ControlType`（[`types.ts:102-116`](../../../packages/schema-core/src/types.ts)）是闭集，
无联合类型控件。按 ADR-002 的两级边界，**新增控件类型属 Level 2（应用代码更新）**——
本版本正是应用发布，可以做，但必须写新 ADR。→ #0（规划侧）+ #1（渲染侧）。

### 2. 扩展 `SchemaModule` 类型 —— 未满足，本版本自解 → #2

核对 [`types.ts:178-182`](../../../packages/schema-core/src/types.ts)：
`SchemaModule = { manifest, schema, ui }`，确无 `validation.rules` / `examples` / `i18n`。
版本文档要求「至少补前三项」，`migrations/*.json` 留 v0.5.0。→ #2。

### 3. 冻结 P0 出站协议字段集合 —— 未满足，需外部信息 → 已决策，#3

仓库内**不存在** v1.19.29 `docs/config.yaml` 的任何副本（全仓库 grep 只在
`config-model` / `apps/web` 的版本号常量里命中 `1.19.29` 字符串）。
`upstream-divergences.md` 待核对项 2 仍是「待核对」。

**已决策（本轮确认）**：把上游 `docs/config.yaml` 按 tag 取回并 **vendor 进仓库**，
连同来源 URL、tag、commit SHA、取回日期一并存档，核对脚本对它做断言。→ #3。

### 附加：内置 Bundle 签名会在 #6 失效 —— 版本文档未列，本版本自解 → #6

[`builtin.ts:37-67`](../../../packages/schema-registry/src/builtin.ts) 的
`BUILTIN_MANIFEST` 携带 `files[].sha256` 与 Ed25519 `signature`，注释明确写着签发用的
bootstrap 私钥「已在签名后立即销毁，从未存储」。#6 起 `BUILTIN_MODULE` 的内容必然改变
→ 文件哈希改变 → manifest 改变 → **签名必然失效**，`verify.test.ts` 会红。

ADR-010 的生产密钥托管（GitHub Environment `schema-release` + `SCHEMA_SIGNING_KEY_B64`

- ≥2 人审批）**尚未建立**：`.github/workflows/` 里没有任何签名 job，`schema-cli` 也没有
  keygen 子命令。但 Bundle 下载与通道是 v0.5.0 范围（版本文档 Out of scope 明列），
  本版本的内置 Bundle 是**编译进应用、从不下载**的离线兜底，其签名是自洽性检查而非供应链
  闸门。

**结论**：沿用 v0.1.0 #8 的既有做法——离线生成一次性 bootstrap 密钥对、重签、内置新公钥、
销毁私钥；`builtin.ts` 的注释原样保留（生产密钥重签仍是 v0.5.0 的义务）。为防止
#7–#11 逐模块改内容时哈希悄悄过期，#6 同时交付一条**再签发回归断言**。不需要你决策。

## 切片详情

### #0 基线校正与 `schema-core` 判别式联合规划

**目标**：让 `oneOf` / `anyOf` 判别式联合规划出可渲染的字段树，而不是落进 `unknown`。

**覆盖**：FR-SCHEMA-02（联合类型，规划侧）。

**依赖**：无。

**涉及文件**

- 修改：`packages/schema-core/src/types.ts`（`ControlType` 加 `'variant'`；`PlannedField`
  加联合分支元数据；`UiFieldSpec` 加 `variantLabels?`）
- 修改：`packages/schema-core/src/form-plan.ts`（`inferControl` 加联合分支；`planField`
  在 `control === 'variant'` 时规划命中分支）
- 修改：`packages/schema-core/src/form-plan.test.ts`
- 新建：`docs/adr/ADR-019-discriminated-union-control.md`
- 修改：`docs/adr/README.md`、`README.md`、`docs/releases/README.md`、
  `docs/requirements-traceability.md`（见「现状核对」表中标 #0 的行）

**实现要点**

- **判别键的发现是声明式的，不硬编码 `type`**：分支里凡是 `const` 或单值 `enum` 的属性
  即候选判别键；多个候选时取所有分支都具备的第一个（按属性声明顺序）。九种 P0 出站协议
  按 `type` 判别只是这条通用规则的一个实例——`proxies` 的 Schema 不需要任何特殊照顾，
  这正是 FR-SCHEMA-06 要保住的性质。
- 找不到判别键时**不报错也不猜**：退回 `unknown` 控件（与今天行为一致），并在
  `PlannedField` 上标记原因。合成的坏 Schema 不该让表单崩掉。
- **命中分支的属性规划为 `children`**，路径不变（联合不引入额外路径层级）——
  `proxies[0].password` 的路径必须是 `['proxies', 0, 'password']`，不能是
  `['proxies', 0, 'ss', 'password']`，否则 YAML 回写路径就错了。
- **切换判别值不得删除任何字段**（E4）：规划器是纯函数、不写文档，本身做不到删除；
  要断言的是「文档里存在但当前分支未声明的属性，仍然作为 unknown 字段被规划出来」——
  与基础/高级模式「不丢字段」是同一条保证的另一个入口。这是本片的核心断言。
- `MAX_NESTING`（当前 8）对联合分支同样生效，恶意 Schema 不能靠嵌套联合把规划器打爆。

### #4 `validation.rules` 受限 DSL 求值器

**目标**：让跨字段、跨对象的互斥与依赖约束能由 Bundle 声明，而不必改应用代码。

**覆盖**：FR-SCHEMA-03（互斥与依赖字段）。

**依赖**：#2。

**涉及文件**

- 新建：`packages/schema-core/src/rules.ts`、`src/rules.test.ts`
- 修改：`packages/schema-core/src/index.ts`

**实现要点**

- **一个新算子都不加**（NFR-SEC-05 / ADR-002）。互斥用 `{ op: 'not', of: { op: 'and',
of: [{ op: 'exists', path: 'a' }, { op: 'exists', path: 'b' }] } }` 表达；依赖用
  `{ op: 'or', of: [{ op: 'not', of: {...exists a} }, {...exists b} ] }`。求值器只是把
  已有的 `evaluateCondition` 应用到规则列表上并产出 `ValidationIssue`。
- **规则的作用域是模块根**，`$.` 前缀寻址已由 `condition.ts` 支持；跨对象（例如
  `proxies[]` 的每一项）用 `path` 上的通配段展开，展开逻辑在本片实现且**上限固定**
  （匹配项数量有上限，避免 1 MB 配置 × N 条规则的组合爆炸）。
- 产出的问题**只带路径与规则 id，不带命中的值**（NFR-SEC-03），要有用真实密钥值驱动的
  否定用例。
- `severity` 由规则自己声明；`blocking` 仍由 `@mcs/validator` 的既有口径统一判定，
  本片不重新发明规则。
- **记录 DSL 表达不了的约束**：核对上游时若发现某条约束（例如「`port` 与 `ports`
  互斥且至少其一」的复杂变体）无法用封闭算子集表达，写进 ADR-019 的「DSL 演进输入」
  小节或新建记录，**不要偷偷升级成应用代码里的 if**。ADR-002 已接受这个代价，
  但代价必须可见。

### #9 `proxies` 模块 A：联合骨架 + HTTP / SOCKS / SS / Trojan

**目标**：把九种出站协议的判别式联合骨架搭起来，先交付四种结构较简单的协议。

**覆盖**：PRD §8.3 出站节点 P0（前四种）；FR-SCHEMA-02 在真实字段上复验。

**依赖**：#0、#4、#6。**本版本的核心风险片**——版本文档「本版本要回答的问题」

- 修改：`packages/schema-builtin/src/index.ts`、`packages/schema-registry/src/builtin.ts`（重签）

**实现要点**

- `proxies` 是数组，元素是按 `type` 判别的 `oneOf`。**共享字段（`name`、`server`、
  `port`、`udp` 等）放 `$defs` 并由各分支 `allOf` 引入**——`$ref` 只允许本地

  用例要显式证明：#10 新增的五种协议只往 `config.schema.json` / `ui.schema.json` 加分支，
  `packages/form-renderer` 与 `apps/web` 一行不改。为此本片就要有一条「向联合追加一个
  合成分支，渲染即可用」的用例（与 M0 的 FR-SCHEMA-06 用例同一手法，但在真实模块上）。
- 敏感字段复验 NFR-SEC-02：`password`（SS / Trojan）必须默认遮罩。
- 若判别式联合确实表达不出某种协议的差异，**立刻停下来记录**并按版本文档风险表的缓解
  路径处理（为协议选择器单独设计控件类型已在 #0/#1 做完；若仍不够，说明需要 Level 2
  的进一步扩展，必须写进 ADR-019 的补充而不是在渲染器里加 if）。
- 逐字段对 `UPSTREAM_P0_FIELDS` 双向断言；四类 examples 齐备。

**执行时修正**

- **本片核心风险的答案是"是，但有一个具体的、已记录的边界"**：判别式联合机制
  （#0/#1 在合成样例上证明）在真实、混乱的 Mihomo 协议字段上依然成立——`password`
  在 http/socks5/ss/trojan 四种协议上都被自动判定为 `secret` 控件（NFR-SEC-02，
  无需显式 UI 覆盖）；新增第五个分支（合成 `vmess` + `uuid`）不需要改
  `packages/form-renderer`/`apps/web` 任何一行，`packages/schema-core` 也不用改
  ——同一份探测 harness 立刻能用。这不是"判别式联合表达不出协议差异"（第 662 行的
  停下条件），是另一个更窄的边界：
- **`config.schema.json` 描述的是数组的单个元素，不是 `proxies:` 整个数组**：
  `buildFormPlan` 只在具名字段上识别 `oneOf`/`anyOf`（`planField` 的职责），从不
  识别它正在规划的 schema 自己根层级的联合（`planObject` 只看 `.properties`）。
  一个 `proxies[]` 元素本身没有包装键（就是 `{name, type, server, ...}`），在
  schema 里为了迁就今天的规划器硬套一个假包装键，会让这个模块的存储内容不再如实
  对应磁盘上真实文档的样子——这是每个模块目前为止都成立的不变量，不该为这一个
  模块破例。所以：存储的 schema 保持诚实，`builtin.test.ts` 自己用一次性包装

  只是指向 `PROXIES_MODULE` 真实的 `$defs`/`oneOf` 而非临时构造的）驱动
  `buildFormPlan` 来完成这条证明，包装只在测试里发生，从不进入存储模块。
- **由此推出的、真正留到 #14 的缺口**：`buildFormPlan(PROXIES_MODULE, 整份真实
文档)` 目前还不能端到端直接调用——数组不是 record，`planObject` 会把它当成

  要做的事，处理原则与 general/inbound 共享文档根的缺口相同（同一小节记录）。
  `manifest.root: ['proxies']` 保留：它仍然如实记录这个模块拥有文档里的哪条路径，
  只是"路径"与"能直接喂给 `buildFormPlan`"这两件事，对 `proxies` 这一个模块来说
  第一次分开了。
- 通用的 `describe.each(MODULES)` 表格测试对 `proxies` 不适用（`collectSchemaPaths`
  只走 `.properties`，看不到 `$defs`/`oneOf`），改写了专用的
  `describe('proxies module', ...)` 块，含专用的 `collectProxyFieldPaths`（读
  `$defs` 还原 `_shared.<key>`/`<protocol>.<key>` 路径，与 `UPSTREAM_P0_FIELDS.proxies`
  的既有命名对齐）。

  = `sha256:60de76a35a6cbf7b4fa4a20f5c257c24345d1d635ab1aa3877022a1997ef413c`，
  17 858 765 字节。注释必须写明「上游未发布 checksum 清单，此值取自 GitHub asset
  digest，见 D-003」——不写来源的话，后人无法判断这个值可不可信。
  **digest 不匹配就失败退出，不重试、不降级**。
- 单测覆盖多架构选行逻辑：命中行、未填行（必须明确报错）、digest 不匹配三条。
- **单测不下载**：把下载器拆成「取字节的注入端口」+「校验与解压的纯函数」，
  单测只测后者（含 digest 不匹配的否定用例）。真实下载只在 CI job 里发生。
- CI job 约束（ADR-010 §4 的同一姿态）：`permissions: contents: read`，不引入任何
  第三方 action，**不给该 job 任何 secret**。执行外部二进制的面已经扩大了，
  不能再叠加凭据。
- 配置测试用 `mihomo -t -f <模板产物>`，退出码非 0 即失败。job **阻断**（不是
  `continue-on-error`）——PRD §13.5 把「内置模板未通过内核测试」列为发布阻断项。
- **「仅代理集合 + 自动选择」模板带一个本版本未建 Schema 的 `proxy-groups` 段**（E6）。
  它必须照样通过内核测试——这是本版本对「未覆盖的段原样保留且内核仍可用」最有力的
  一条证据，比任何 golden 断言都直接。若内核对该段报错，说明模板本身写错了，
  修模板，不是把该段删掉绕过。
- 若 v1.19.29 的内核对某个模板报错而 PRD 认为该配置合法，按既有规则以上游为准，
  追加 D-xxx，**不得静默改模板去迎合**。
