## 工程约束（实现时必须遵守，逐片适用）

- Node ≥ 20.11 / pnpm 10。**每片验收都是 `pnpm run check` 和 `pnpm run format:check` 两条**，
  后者 CI 单独跑、最容易漏。
- 覆盖率阈值 85% 在 `vitest.config.ts` 强制，**不得放宽**。新增的 `apps/web/src/**` 代码
  同样计入覆盖率 include。
- `packages/**` 禁止 `node:fs`（ESLint 强制）与任何网络调用（CI `no-network-egress` job
  强制，白名单是路径精确的）。**本版本所有新代码都不进 `packages/**`**，唯一例外是 #2 的
  一处删除。
- `packages/**` 禁止 `import '@capacitor/*'`（ESLint 强制）。Capacitor 只出现在
  `apps/web/src/platform/capacitor.ts`（单一接触点）与 `apps/android`。
- 工作区内部包直接导出 TypeScript 源码（ADR-007），不新建构建步骤。
- 用户可见文本一律走 `apps/web/src/i18n` 的 key，`zh-CN.json` 与 `en.json` 同步新增
  （`i18n.test.ts` 的键集合对等检查会拦下漏项）。**能力门页面也不例外**——但它必须在
  i18n 模块可用之前就能渲染，见 #1 实现要点。
- 错误与日志消息不得包含配置值（NFR-SEC-03）。本版本新增的分享失败、存储不足、SAF
  取消三类消息尤其容易带上文件内容或路径，一律只带类别。
- `packages/test-fixtures/fixtures/**` 是字节敏感 Golden 文件，不格式化、不顺手整理。
- PRD 与上游实际行为冲突时以上游为准，记入 `docs/upstream-divergences.md`。

### #1 WebView 基线实测、ADR-027 与启动能力门

**目标**：把「本产品要求的最低 Chromium 版本」从隐式（Vite 默认 target）变成显式冻结的
数字，并让不达标的 WebView 看到一句人话，而不是白屏。

**覆盖**：PRD §11.4；决策 G2；退出条件 1、8 的前置。

**依赖**：#0。

**涉及文件**

- 新建 `docs/adr/ADR-027-minimum-webview-baseline.md`，并在 `docs/adr/README.md` 表格加行
- 修改 `apps/web/vite.config.ts`：显式写 `build.target`（不再吃 Vite 默认值）
- 新建 `apps/web/src/platform/capabilities.ts` + `capabilities.test.ts`：
  `detectMissingCapabilities(global)` 返回缺失能力名数组（纯函数，注入 global 便于测试）
- 修改 `apps/web/src/main.tsx`：挂载 React 之前先跑探测，缺能力则渲染能力门
- 新建 `apps/web/src/platform/UnsupportedBrowser.ts`（**不是 .tsx**）+ 测试

**实现要点**

- **先实测再写数字**：用 `adb shell dumpsys package com.google.android.webview | grep versionName`
  在三台 AVD 上各取一次真实 `versionName` 写进 ADR-027 的表。ADR-013 记的是
  2026-08-12 的值（API 29 → Chrome 74、API 36 → 133），镜像可更新，**不得直接引用旧值当现状**。
- 冻结口径建议 **Chromium ≥ 107 / Firefox ≥ 104 / Safari ≥ 16**（Vite 6
  `baseline-widely-available` 的实际含义），把它写死进 `build.target` 而不是留默认值。
  这比 PRD §11.4「最近两个主要版本」更宽松，不构成偏离。
- 探测**按运行时 API 探，不按 UA 号探**：现有代码已经在用 `String.prototype.replaceAll`
  （`i18n/index.ts:76`，Chrome 85+）、`Array.prototype.at`、`Object.hasOwn`；再加
  `indexedDB`、`Worker`、`crypto.subtle`。UA 嗅探在 WebView 上不可靠，而这些正是缺了就
  白屏的东西。

### #10 `@noble/ed25519` 后端 + WebView 更新链路复验

**目标**：兑现 ADR-013 推迟到本版本的纯 JS 验签后端，让 Bundle 安装/回滚在**不支持
Ed25519 WebCrypto 的 WebView** 上真的能跑。

**覆盖**：NFR-SEC-04 的 Android 面；决策 G3；退出条件 7。

**依赖**：#0（更新源接线）、#3（产品壳）。

**涉及文件**

- 新建 `docs/adr/ADR-028-pure-js-ed25519-backend.md`，`docs/adr/README.md` 加行
- 修改 `apps/web/package.json`：新增 `@noble/ed25519`（精确版本）
- 新建 `apps/web/src/bundle/noble-verifier.ts` + `noble-verifier.test.ts`
- 修改 `apps/web/src/bundle/verify-options.ts`：按能力选择后端
- 修改 `packages/schema-registry/src/verify.ts:7-16` 的注释（只改注释）

**实现要点**

- **调用方一行不改**：`Ed25519Verifier` 端口是 ADR-013 就定好的接口，本片只是提供
  第二个实现并在 `verify-options.ts` 里选。`packages/schema-registry` 不加任何依赖。
- 选择策略要**探测而非假设**：启动时用一个已知向量试一次
  `crypto.subtle.verify({name:'Ed25519'}, …)`，成功用原生、失败用 noble。不要按
  UA 或 Android 与否判断——ADR-013 已经证明 WebView 版本与 OS 版本脱钩。
- noble v2 的 `verifyAsync` 依赖 `etc.sha512Async`，其默认实现走
  `crypto.subtle.digest('SHA-512')`。ADR-013 实测两台设备的 `digest` 均可用，
  所以这条路径在目标 WebView 上成立；**但仍显式注入我们自己的 sha512 实现**，
  不依赖库的默认值在未来版本里保持不变。
- 测试用 RFC 8032 §7.1 的固定向量（`tools/webcrypto-probe/probe.html` 里已有一组），
  正例 + 篡改签名 + 篡改消息 + 错公钥四条，并加一条「两个后端对同一输入给出相同结论」
  的一致性用例。
- 供应链姿态写进 ADR-028：精确版本锁定（非 `^`）、`pnpm-lock.yaml` 记录 integrity、
  依赖落在 `apps/web` 而非 `packages/**`、CI 的 `no-network-egress` 覆盖面不变。
  ADR-010 把「引入密码学依赖」本身列为供应链风险，这条决策是在「自己写密码学」与
  「引入一个被广泛审计的零依赖实现」之间取后者，理由要写足。
- 复验（退出条件 7）：在 API 29 与 API 36 AVD 上各跑一次 #0 的同一条链路
  （检查更新 → 安装 → 回滚），产物走 `adb reverse` 把宿主机端口映进设备 `localhost`
  ——ADR-013 已经踩过 `10.0.2.2` 不是可信来源、`crypto.subtle` 整体缺失的坑，
  照抄那个做法。API 29 上预期会先撞 #1 的能力门，处理见「风险」R1。
