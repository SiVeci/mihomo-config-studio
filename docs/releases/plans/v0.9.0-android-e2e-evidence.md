## 过程中确认/修复的三个真实工程问题（均已写进代码注释，这里合并记录一次）

1. **`pm clear`/`am kill` 打自己会打死测试本身**。Android 的 instrumented test
   与被测 app 天然同进程运行；一个测试对自己的目标包调用 `pm clear`（强制停止在先）
   或 `am kill`，杀的就是这个测试自己所在的进程。实测：`@Before` 里的 `pm clear`
   让"无论哪个测试先跑"都在几十毫秒内报 "Instrumentation run failed due to Process
   crashed"，`adb logcat` 能看到 `PACKAGE_DATA_CLEARED` 与
   `AndroidRuntime: VM exiting`。**修法**：改用
   `androidx.test:orchestrator` + `clearPackageData` ——由 Orchestrator（独立进程）
   在测试之间做清理，而不是测试自己对自己动手。`am kill` 同样的问题在
   "process kill" 场景上无解——见下一条。
2. **"进程被杀后重启仍保留编辑"这一条，结构上无法在单个自包含测试方法里自动化**。
   Orchestrator 只改变"两个测试方法之间"发生什么，一个测试方法执行期间，它与被测
   app 仍然是同一个进程，因此该测试不可能 `am kill` 自己的目标包之后还能继续跑
   断言。**处理方式**：这一条真实的进程杀死验证，仍然只有 v0.6.0 #8 的人工验证
   （`docs/releases/plans/v0.6.0-android-evidence.md`）作为证据，本片不重新声称
   已自动化——如实记录，不静默降级成"导航切换"就当作等价物。本片新增的
   `editSurvivesNavigatingAwayAndBackAfterAutosave` 测的是一件相关但更窄的真实
   事实（自动保存确实落到 IndexedDB，靠"离开项目列表再回来"强制一次冷读，而不是
   靠内存中从未忘记的组件实例），场景改名清楚地反映了它测的是什么，不是原计划
   "进程被杀"场景的等价替代。
3. **`选择文件`（SAF 打开）无法可靠找到本片自己写到设备上的输入文件**。最初做法是
   用 shell 重定向把测试用 YAML 写到 `/storage/emulated/0/Download/`——文件本身
   立刻真实存在（`sha256sum` 马上能读到），但在系统 SAF 选择器的 Downloads 列表里
   持续不可见。**五种独立验证过"单独测试时确实有效"的手段全部在本测试套件自己的
   连续自动化节奏下不可靠**：`MEDIA_SCANNER_SCAN_FILE` 广播（发出即返回，不等
   索引真正完成）、轮询 `content query`（等满 15 秒仍未命中）、MediaStore 自己的
   同步 `content insert`（`content query` 确认立即可查，但选择器仍然看不到）、
   强制重启 DocumentsUI 换一个没有缓存旧列表的新进程、外加固定延时——组合使用
   仍然复现失败。真正的分野**不是等待时间不够，而是"写入方式"本身**：凡是本测试
   套件通过真实 SAF 另存流程（`saveAsInDocumentsUi`）自己写出的文件，重新打开时
   每一次都立刻可见。**修法**：输入侧改用"粘贴 YAML 文本"（`ImportPanel.tsx` 的
   `<textarea id="import-paste">`）而不是预置设备文件走 SAF 打开——完全绕开这个
   问题，SAF 打开仅在"重新打开本套件自己刚导出的文件"这一步使用，此时文件是通过
   真实 SAF 写出的，问题不存在。

## 未解决、如实记录为 Partial 的问题（本片停止点）

切换到"粘贴 YAML 文本"后，SAF 打开可见性问题消失，但暴露了一个**新的、独立的、
未解决**的 UI 时序问题：`opensEditsSavesAndReopensRoundTrip` 与
`editSurvivesNavigatingAwayAndBackAfterAutosave` 在"粘贴导入 → 切到表单 tab →
勾选 `/ipv6`"之后，紧接着的 `tapText("导出")`（前者）或
`waitForText("保存中…")`（后者）稳定找不到目标。已尝试且均未解决：

1. `UiScrollable(UiSelector().scrollable(true)).scrollIntoView(...)`（原有
   实现）——失败。
2. 在 (1) 失败后追加手动滑动重试循环（最多 12 次 `device.swipe`，每次滑动后
   重新 `findObject`）——仍然失败，两个场景报的是同一句
   `'导出' never appeared` / `'保存中…' never appeared`。

尚未确认根因是滚动容器识别错误、粘贴长文本后布局与预期不同，还是别的原因——按
"同一个失败已尝试两种不同修法仍然失败，停下来记录，不要继续试"的既定原则，本片
到此为止，不再继续猜测第三种修法。`cancelingThePickerDoesNotCrashTheApp`（不依赖
导入/滚动到导出）与 `shareOpensTheSystemChooser` 的分享弹出部分未复现这个具体
症状，但完整套件运行还受到下面这条独立噪声的干扰，没有拿到一次"全部 4 个场景
干净通过"的记录。

## 与本片无关的环境噪声（如实记录，不算在上面的失败里）

- **`dl.google.com` 间歇性 TLS 握手失败**：本机对 Google Maven 仓库的下载
  在同一 URL 上重试即可能从失败变成成功（用 `curl` 单独复现过：连续两次请求
  同一 URL，一次 200、一次握手失败）。多次 Gradle 依赖解析失败（含首次引入
  `uiautomator`/`orchestrator` 时）都是这个原因，与本片代码无关，重试后可解决。
- **`capacitor-cordova-android-plugins:checkDebugAndroidTestDuplicateClasses`
  的 Kotlin stdlib 重复类报错**：`kotlin-stdlib:1.8.22` 与
  `kotlin-stdlib-jdk7/jdk8:1.6.21` 偶发冲突，仅在少数几次调用
  `-Pandroid.testInstrumentationRunnerArguments.class=...` 单测过滤或个别完整
  套件调用中出现，不改任何代码、单纯重跑标准 `connectedAndroidTest`（不带类
  过滤参数）即可绕开，怀疑与上一条同源（部分依赖在某次解析中命中了不一致的
  缓存状态），未继续深挖。
- **Bluetooth 模拟器崩溃**（`com.google.android.bluetooth` 的
  `on_hardware_error`）：已确认与本应用/本测试无关（`logcat -b crash` 里只有
  这一条，时间戳在多次运行中固定不变，说明是历史遗留、并非每次运行新产生）；
  一度怀疑与"分享面板会枚举蓝牙分享目标"有关，禁用蓝牙后复测，同样的
  "Instrumentation run failed due to Process crashed" 依然出现在不同的测试上，
  排除了这个假设。

## 追加调查（同日，第二轮）：真找到了一个真实 bug，但不是全部根因

按上面"下一步建议"里说的，真的用 `uiautomator dump` 在粘贴导入之后立即抓了一次
真实层级快照（`adb shell`，宿主机直接发出，而不是靠这套测试自己的重试逻辑）。
发现的第一件事：**"导出"按钮及同一屏幕上一百多个其他节点，此刻在无障碍树里
确实存在，但 `bounds` 是坍缩的**——要么是 `[0,0][0,0]`，要么被裁剪成
`[63,2400][175,2400]`（宽度非零、高度为零，贴在视口底边）。而 `tapText`/
`tapResourceId` 原有的重试循环，判断"要不要继续滑动"的条件是
`findObject(...) == null`——只要节点在树里就算"找到了"，完全不看它有没有真实
尺寸。两次失败的修法（`UiScrollable` 自动检测、手动滑动重试）都没有改到这一
点，所以都在第一次检查就"假阳性"退出循环，从未真正滑动过，点击自然落空。

**这是一个真实、已确认、已修复的 bug**：`SafRoundTripTest.kt` 新增了
`UiObject2.isLaidOut()`（`visibleBounds` 宽高都大于零才算数），`tapText`/
`tapResourceId` 的三处检查点（初次查找、滑动循环、循环耗尽后的兜底等待）全部
改用这个判断。手动验证过它的前提是对的：用 `adb shell input swipe` 在宿主机
连续滑 3~5 次，"导出"确实会从坍缩状态变成真实、可点击的 `bounds`。

但把这个修复接入测试代码后重跑，三个原本失败的场景**同样的报错原样重现**，
一次没变。加日志追下去后发现了第二件事，比第一件更深：**这套测试用的
`UiDevice.swipe()`（进程内 Java API）和手动 `adb shell input swipe`（宿主机
发出）效果不一样**——`shareOpensTheSystemChooser` 这个最短路径的场景（导入
成功后第一步就是 `tapText("导出")`，完全不经过表单 tab）显示：滑动前
`findObject` 有时还能拿到那个坍缩节点，**只要 `device.swipe()` 真正执行过
一次，`findObject` 此后就再也找不到"导出"了**——连续 12 次滑动 + 额外 15 秒
轮询，全部是 `null`，不是"仍然坍缩"，而是彻底找不到。这和宿主机手动滑动的
结果（几次之内稳定滚到真实坐标）完全对不上。

为了确认到底是"划过头了"还是别的原因，尝试在测试内部用已有的 `shell()` 辅助
函数再拉一次 `uiautomator dump` 做实时对照——这条路本身走不通：无论是否加
`2>&1`、是否改用文件重定向分别捕获 stdout/stderr，测试内部发起的
`uiautomator dump` 每次都是零字节输出、目标文件也没有被创建。最可能的原因是
UiAutomation 的无障碍服务连接同一时刻只能有一个客户端占用，测试自身的
instrumentation 已经占着这个连接，测试内部再起一个 `uiautomator dump` 进程
去抢同一个服务会静默失败——这个诊断手段在"测试运行期间、从测试自己进程内部"
这个场景下不成立，宿主机外部发起（本片前面几轮验证用的方式）不受此限制。

**如实记录**：`isLaidOut()` 这个修复本身是对的、必要的，已保留在代码里；但
它不是这次两个场景失败的完整解释——真正拦住这三个场景的是"进程内合成滑动
手势之后，控件变得（比之前更）不可见"这个更深的问题，根因未确认（怀疑与
Chromium WebView 处理合成触屏手势的抛掷/惯性物理效果，或与 UiAutomator2 客户端
在快速连续手势下的无障碍树缓存/失效时机有关，但都还只是猜测，没有像前面三个
问题那样拿到直接证据坐实）。诊断工具本身（进程内再次 dump）在这个场景下用不
了，是这一轮排查最终停下来的原因，不是"同一个修法试了三次"——是两条独立的
排查路径（改判断条件、再取一次实时快照）都没能把根因坐实，其中第二条在拿到
决定性证据之前就先撞上了工具本身的限制。

## 追加调查（2026-09-06，第三轮）：宿主机独立复现，确认非 app 缺陷、非新增回归

用户直接要求「Android 端跑一遍 SafRoundTripTest 再看看」，借这个机会做了一次
与测试代码完全独立的复现，方法是"接下来谁来做什么"第 1 条建议的宿主机侧路线
（本轮未与测试运行并行，而是先跑一次完整套件观察失败，再单独装 app 手动复现）：

1. **先在 `Medium_Phone_API_29`（Android 10，WebView `74.0.3729.185`）跑了一次
   完整套件**：4 个场景全部失败，报错都是"`新建项目`从未出现"。用
   `adb logcat` + `adb shell uiautomator dump` 现场核对后确认——**这不是本片
   的 bug**：这台设备的 WebView 版本低于本应用记录的最低基线（107，
   [ADR-027](../../adr/ADR-027-minimum-webview-baseline.md)），应用自己的
   能力门正确弹出"浏览器版本过旧 / Browser Version Too Old"提示，属于
   按设计工作，只是选错了模拟器。换到 `Medium_Phone_API_35`
   （Android 15，WebView `151.0.7922.199`，高于基线）重新跑。
2. **`Medium_Phone_API_35` 上重新跑完整套件**：结果与本文件前面记录的完全
   一致——4 个场景 1 个通过（`cancelingThePickerDoesNotCrashTheApp`，全程不
   需要滚动）、3 个失败，报错原样是 `'导出' never appeared`（两个场景）与
   `'保存中…' never appeared`（一个场景）。**说明这不是上次会话遗留的偶发
   状态，是可稳定复现的同一个问题**，本文件"Partial"的判定继续成立，不需要
   改判定。
3. **独立于测试代码，手动装同一个 debug APK，全程只用 `adb shell` 原始命令
   驱动（不经过这套测试的 Java 代码，也不在测试运行期间进行，绕开了上一轮
   "测试进程内部再拉一次 dump 会话冲突"的限制）**：
   - 新建项目后立即 dump：`导出` 按钮确实在无障碍树里，`bounds="[0,0][0,0]"`
     ——与上一轮记录的坍缩现象一致，且这次确认是**从新建项目那一刻起就是
     坍缩状态**，不需要先执行任何操作触发。
   - 从宿主机发出**一次** `adb shell input swipe`（不经过测试的 Java
     `UiDevice.swipe()`）后立即再 dump：`导出` 的 `bounds` 变为真实值
     `[63,997][175,1065]`。
   - 直接 tap 这个真实坐标：导出菜单正确弹出（`导出 config.yaml`／
     `导出 .mcsproj` 均在），行为完全正常。

**结论**：这次复现没有推翻上一轮"进程内合成滑动手势导致 `findObject` 找不到
目标、根因未确认"的判断，也没能进一步坐实那个根因（本轮没有对比"进程内
swipe 执行后紧接着 dump"这一步，那条诊断路径上一轮已确认走不通）。但补上了
两个新的、独立确认过的事实：① 坍缩 `bounds` 是新建项目后**确定性出现**的
初始状态，不是某种偶发时序；② 宿主机外部滑动 + 真实坐标点击这条路径**这次
同样验证有效**，应用自身的导出流程在拿到正确坐标后完全正确——**问题始终
只在自动化驱动层，不在被测应用**，符合本文件从一开始的判断，没有发现新的
应用侧缺陷，也没有发现这是本片之后新引入的回归。判定维持 Partial，不改动。

## 追加调查（2026-09-06，第四轮）：推翻了第二轮的根因判断，定位到真正的现象

用户要求实际动手修，并指定先试"接下来谁来做什么"第 2 条最后那个方向——把
`tapText`/`tapResourceId` 里的滑动从进程内 `UiDevice.swipe()` 改成透过已有的
`shell()` 辅助函数发外部手势。**该修法已实测，无效**；但这一轮用进程内日志拿到
了前三轮一直缺的那块直接证据，**推翻了第二轮"进程内滑动手势与外部滑动效果不同"
这个判断**。三次修法全部失败后按既定原则停止，代码回滚到改动前状态。

### 逐条试了什么、结果如何

1. **改用外部手势**（`shell("input swipe 540 1600 540 400 20")` 取代
   `device.swipe(540, 1600, 540, 400, 20)`）。先在宿主机上核对过这条命令本身
   确实有效（新建项目后 `导出` 的 `bounds` 从 `[0,0][0,0]` 变成
   `[63,997][175,1065]`，与第三轮记录一致）。跑完整套件：**3 个场景原样失败，
   报错一字未变**。
2. **删掉 `UiScrollable` 那一步**（见下方"顺带确认的第二件事"）。跑完整套件：
   **变得更糟——4 个场景全挂**，原本唯一稳定通过的
   `cancelingThePickerDoesNotCrashTheApp` 也开始报 `'选择文件' never appeared`。
   原因是这一步虽然从不成功，却顺带提供了一次数秒级的隐式等待，
   `cancelingThePickerDoesNotCrashTheApp` 从选择器返回后第二次点"选择文件"
   实际依赖了这个等待。
3. **强制清空进程内无障碍节点缓存**（`UiAutomation.setServiceInfo`，框架内部会
   借此调用 `AccessibilityInteractionClient.clearCache()`）。每次滑动后清一次并
   记录清理前后的节点数：**`before=8 after=8`，毫无变化**，失败依旧。这一条只在
   最短路径的 `shareOpensTheSystemChooser` 单场景上验证（该场景失败点最靠前、
   信号最干净），未跑完整套件——因为它连"树能不能回来"这个前提都没通过，跑完整
   套件不会带来新信息。

### 真正的现象（本轮新增的直接证据）

在 `tapText` 里打点记录"此刻本应用包下能查到多少个无障碍节点、都是什么文字"，
`adb logcat` 取回，`shareOpensTheSystemChooser` 这条最短路径给出的序列是：

| 时刻                             | 本应用包下节点数 | 能读到的文字             |
| -------------------------------- | ---------------- | ------------------------ |
| 进入 `tapText("导出")` 时         | **54**           | 导入配置、导入成功、表单… |
| 第一次滑动（外部 `input swipe`）后 | **8**            | **一个都没有**            |
| 之后 12 次滑动 + 15 秒轮询期间     | **8**            | 一个都没有                |

**这个 WebView 只要发生一次滚动——无论手势是进程内发的还是外部发的——它整棵
Chromium 虚拟视图树就从"本 instrumentation 进程看到的"无障碍树里整体消失，
只剩 8 个原生 `Activity` 外壳节点，且在该测试方法剩余时间里再也不回来。**

同时确认这不是"节点还在、只是 `bounds` 坍缩"（第二轮的猜测方向之一），也不是
客户端缓存过期：

- `findObject` 返回的是 `null`，且整个包下连一个带文字的节点都查不到，不是
  查得到但尺寸为零。
- 上面第 3 条已证明清缓存无效。
- **与此同时，外部独立的无障碍客户端看同一块屏幕是完全正常的**：本轮在测试运行
  期间从宿主机连续截屏（`adb exec-out screencap`），`导出` 按钮清清楚楚渲染在
  屏幕上、位置正确；第三轮也已确认宿主机 `uiautomator dump` 此时能拿到完整树和
  正确 `bounds`。

所以问题既不在被测应用（应用渲染和行为都正确），也不在"手势由谁发出"（外部手势
和进程内手势一样会触发这个现象，第二轮的判断在这一点上是错的），而在
**滚动之后、这个 instrumentation 进程自己那条无障碍连接上，WebView 的虚拟视图树
被整体拆掉了**。拆除本身的根因（Chromium 在何种条件下对某条无障碍连接停止暴露
虚拟树）仍未确认。

### 顺带确认的第二件事：`UiScrollable` 那一步从来就不可能成功

同一批日志显示，`tapText("导出")` 里的
`UiScrollable(UiSelector().scrollable(true)).scrollIntoView(...)` **单次耗时 87 秒**
（10:00:50.766 → 10:02:18.021），而且正是这一步第一个把节点数从 54 打到 8。
原因在宿主机 dump 里看得很清楚：**这个页面上没有任何一个节点是
`scrollable="true"`**（整页滚动由 Chromium 文档自身承担，不对外暴露成可滚动
节点），所以它只能一路搜到 `setMaxSearchSwipes` 上限再放弃。

但如上面第 2 条所述，**单独删掉它反而让通过数从 1 个掉到 0 个**，因为
`cancelingThePickerDoesNotCrashTheApp` 依赖了它顺带产生的隐式等待。这一条如实
记录为"已确认是死代码且代价高昂，但不能孤立删除"，留给后续连同等待策略一起
处理，本轮不做半步改动。

## 接下来谁来做什么

若要把这条转成 Done，下一次会话可以从这些方向继续，不需要重新发现本片已经
确认过的问题（含两轮追加调查）：

1. ~~不再尝试从测试进程内部用 `shell()` 起第二个 `uiautomator dump`~~——
   已确认这条路因无障碍服务连接冲突走不通，且第三轮复现已经拿到了"外部滑动
   有效、坍缩状态确定性出现"的独立证据，不必再重复这一步诊断。
2. ~~怀疑"进程内合成滑动手势"本身，改用外部 `shell("input swipe ...")`~~——
   **第四轮已实测，无效**，且这一轮证明外部手势和进程内手势会触发完全相同的
   现象，"两者效果不同"这个前提本身就是错的。同一轮里"删掉 `UiScrollable`"
   和"强制清空无障碍节点缓存"也都试过、都无效（清缓存那条还顺带排除了
   "客户端缓存过期"这一整类解释）。**这三条不必再重试。**
3. 真正待验证的假设，是第四轮定位到但未坐实的那一个：**滚动之后 Chromium 为何
   在这条 instrumentation 无障碍连接上整体停止暴露虚拟视图树**。可以从这几个
   方向查，都还没试过：
   - 用 `adb shell dumpsys accessibility` 在"滚动前 / 滚动后"各取一次，对比这条
     连接的状态与已注册客户端，看树是真被拆了还是只对这条连接不可见。
   - 换一条连接重新拿树：`Instrumentation.getUiAutomation(flags)` 传入与当前
     不同的 flags 会强制重建 UiAutomation 连接，验证"新连接能看到完整树"
     （宿主机 `uiautomator dump` 已表现出这个特征）是否在进程内也成立。
   - 绕开滚动本身：Chromium 的虚拟节点支持无障碍动作，可试
     `ACTION_SHOW_ON_SCREEN`（让 DOM 自己把目标滚进视野，不发合成触屏手势）
     或直接对节点 `performAction(ACTION_CLICK)`。注意后者改变的是"怎么点"
     而不是"点什么"，采用前应先确认它仍算真实的端到端交互。
   - 查 WebView 侧是否有"无障碍自动关闭"类行为（Chromium 有在客户端长时间
     不查询时自动停用无障碍的机制），确认它与本现象是否相关。
4. 独立于上面：`UiScrollable` 那一步已确认是死代码且单次耗时约 87 秒（第四轮），
   但不能孤立删除——`cancelingThePickerDoesNotCrashTheApp` 依赖了它顺带产生的
   隐式等待。删它必须同时补上一个显式等待，一并改、一并验证。
5. 如果排查后仍然不稳定，考虑改变验证策略本身（例如场景拆分得更细、减少每个
   `@Test` 里的步骤数，降低单次失败影响的场景数），而不是继续增加同一个
   `tapText`/`tapResourceId` 辅助函数的重试层数。
