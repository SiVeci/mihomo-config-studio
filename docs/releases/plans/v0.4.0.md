## 上游事实（本轮实测，2026-08-25）

### `rule-providers` 的 `format: mrs` 对 `behavior` 的取值约束 —— 先决项，**已核实**

依据是仓库内已 vendor 的 v1.19.29 官方 `docs/config.yaml`
（`packages/test-fixtures/fixtures/upstream/mihomo-v1.19.29/config.yaml`，
tag `v1.19.29`、commit `e26714a1`、blob `0598d098`，见 `SOURCE.md`）。逐行核对结果：

| 行            | 原文要点                                                                                           |
| ------------- | -------------------------------------------------------------------------------------------------- |
| 1860          | 「mrs类型ruleset，目前仅支持domain和ipcidr(即不支持classical）」                                   |
| 1862–1870     | `behavior=domain` 与 `behavior=ipcidr` 各自的 `format=yaml`/`format=text` → mrs 转换               |
| 1872–1876     | 唯一的 `format: mrs` 实例：`type: http` + `format: mrs` + `behavior: domain`                       |
| 1847/1855     | `behavior: classical` 实例，均**不带** `format`（默认 yaml）                                       |
| 1880          | `type: inline` 的 `behavior: domain # classical / ipcidr`                                          |
| 272–273 / 365 | 另一条约束：被 `fake-ip-filter` / DNS fallback 引用的 RULE-SET，`behavior` 必须是 domain/classical |

**结论**：`format: mrs` ⇒ `behavior ∈ {domain, ipcidr}`，`classical` 被明确排除。
与 PRD §8.3「规则集合」P0 范围「Classical/Domain/IPCIDR、YAML/Text/MRS」**不构成矛盾**
——PRD 列的是各维度的取值集合，没有声称三×三全组合合法。故**不新增 D-xxx 差异记录**，
只在 `upstream-divergences.md` 的「待核对项」表把该行从「待核对」改为「已关闭」并写明依据
与日期（#0）。

**证据分级，如实记录**：本条是**文档级证实**（钉死版本自带的官方示例配置 + 官方
Meta-Docs 源码），不是**内核级实测**。内核级实测的落点是 #17 —— 「规则集合分流配置」
模板会包含一条 `format: mrs` + `behavior: domain` 的 `rule-providers` 条目，由 CI 的
`core-config-test` job 用真实 `mihomo -t` 跑过（该 job 的运行方式见决策 E8：推分支到
`origin` 触发 CI，本机不执行外部二进制）。

**交叉核对已于执行阶段补齐（#0，2026-08-25）**：编制阶段用 `WebFetch` 拉取
`raw.githubusercontent.com/MetaCubeX/Meta-Docs/.../rule-providers/index.md` 做第二来源
交叉核对被本环境的网络策略拒绝（"Unable to verify if domain ... is safe to fetch"）；
执行 #0 时改用 `gh api repos/MetaCubeX/Meta-Docs/contents/...`（GitHub API，走 `gh` CLI
而非 `WebFetch` 工具）成功拉取，原文「mrs目前 behavior 仅支持 domain/ipcidr」与 vendor

## 本轮确认的决策

这些是编制期已判定、实现时必须遵守的口径。**不需要你逐条确认**，但会体现在对应 ADR 里。

| 编号 | 决策                                                                                                                                                                                                                                                                                                                                                                                |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| E1   | **`rules`/`sub-rules` 走声明式「规则类型目录」，不走 JSON Schema 表单**。目录是 Bundle 数据（`schema-builtin/modules/rules/rule-types.json`），描述每种规则类型的 payload 形态、是否需要 target、参数与文档链接。新增一种规则类型只改数据、不改应用代码——FR-SCHEMA-06 的同一条性质在规则侧成立。需要扩 `SchemaModule`（ADR-002 Level 2）。写 **ADR-021**                            |
| E2   | **虚拟化与关系图一律自建，不引入任何新的运行时依赖**（不引 react-window / @tanstack/virtual / d3 / elkjs / cytoscape）。理由与既有先例一致：自建 hash router、自建 i18n、零依赖手写 ZIP（ADR-018）；离线优先（NFR-SEC-01/退出条件「离线可运行」）与 Android WebView 体积都不欢迎新依赖；关系图只需要**分层 DAG**（节点/Provider → 组 → 规则），不需要通用图布局引擎。写 **ADR-022** |
| E3   | **主列新增「表单 / 规则 / 关系图」视图切换，用组件内 state，不新增路由**。依据 PRD §7.2「中间：图形化表单、列表、拖拽排序和关系图」与 §7.3 Android 底部导航「配置、关系、YAML、问题」。副产品是惰性挂载——10,000 条规则的列表与关系图不会在用户没看它们时被渲染。`router.tsx` 的「路由数是否超出精确匹配」注释按此判定更新为「未超出」                                               |
| E4   | **批量操作走新的 Worker 消息 `applyBatch`，一批补丁包在**一次** `HistoryStack.record()` 里**。既有 `applyPatch` 是单补丁，逐条发送必然产出多条历史项，直接违反退出条件 4。`applyBatch` 语义为全成功或全不改（任一补丁抛错则整批回滚到调用前文本），失败不留半成品。写 **ADR-023**                                                                                                   |
| E5   | **不扩 `detectCycles` 的边类型**。版本文档退出条件 6 只要求「循环引用被阻断并能展示环路路径」，既有两类边（proxy-groups 嵌套、dialer-proxy）已覆盖 PRD §8.5 FR-REL-05 的验收要点。#4 只把 `detectCycles` 的结果接进流水线并置为 `blocking: true`，#13 把 `Cycle`（名称序列）画在图上。`rule-providers` 不构成引用环（规则集合不引用规则集合），无需新边                             |
| E6   | **FR-RULE-04 的四类检查一律 `severity: 'warning'`、`blocking: false`**，与 v0.3.0 #13 的 `securityStage` 同一口径：静态分析不得声称与内核运行时等价（PRD §8.6 末句、NG-07），一条不能保证等价的判断没有资格阻断导出。唯一例外是「缺失 RULE-SET / 缺失策略」——那是**引用完整性**问题，归 #4 的 `referenceStage`，按缺失引用的既有口径判 `error` 且阻断                               |
| E7   | **「明显遮蔽」宁可漏报不可误报**（版本文档风险表原话）。只检测**同类型、同 target 语义下的真包含**（如 `DOMAIN-SUFFIX,a.com` 在前、`DOMAIN,x.a.com` 在后且 target 不同），不做跨类型推理、不做 GEO/RULE-SET 内容展开（内容在远端文件里，本工具从不抓取——ADR-005）。检测不到就不报                                                                                                   |
| E8   | **内核测试走 CI，本机不下载也不执行内核二进制**（2026-08-25 答复 Q1）。切片分支 push 到 `origin` 触发 `core-config-test` job；**#0 完成后立刻首推**，让另外四个 job 也第一次真实验证。退出条件 7 的证据 = 该 job 的 run URL + 五个模板各自的 `mihomo -t` 退出码。详见「待你确认的问题」下的 E8 小节                                                                                 |
| E9   | **「Android 生成目标配置」是普通 Mihomo YAML，不引入平台专属产物格式**（2026-08-25 答复 Q2）。以 `tun` 为核心 + `platforms: ["android"]`；追踪表 §8.8 那句「依赖尚未设计的平台专属产物格式」与代码现状不符，由 #17 一并改掉。详见 E9 小节                                                                                                                                           |

## 工程约束（每片实现时都适用）

- Node ≥ 20.11 / pnpm 10。验收 = `pnpm run check`（typecheck + lint + test）**和**
  `pnpm run format:check`。后者在 CI 是独立步骤，**最容易漏**。
- 覆盖率阈值（行 / 函数 / 语句 85、分支 80）在 `vitest.config.ts` 强制，**不得放宽**。
  新增文件落在既有 `packages/*/src/**`、`apps/web/src/**` glob 内，自动纳入统计。
- 追踪表口径：**标 Done 必须能指向具体测试文件**，否则记 Partial 并写明缺口。
- `packages/**` 禁止 `node:fs`（ESLint `no-restricted-imports`）与任何网络调用
  （CI `no-network-egress` job 用 grep 拦 `fetch|XMLHttpRequest|WebSocket|sendBeacon`）。
  **本版本的直接后果**：新模块的 `examples/*.yaml`、`rule-types.json` 不能在运行时读盘，
  由 `import ... with { type: 'json' }` 或测试文件读取；关系图与规则编辑器**绝不因为
  要「解析 RULE-SET 内容」而发起任何请求**（ADR-005）。
- 工作区内部包直接导出 TypeScript 源码（ADR-007）：`exports` 指向 `./src/index.ts`。
- 用户可见文本一律 i18n key，不写字面量（ADR-016）。中英资源文件 key 集合必须相等，
  由 `apps/web/src/i18n/i18n.test.ts` 的双向差集断言强制；模块自带 `i18n/*.json` 同理。
- 错误与日志消息不得包含配置值（NFR-SEC-03）。**本版本高危面**：规则行本身就是用户
  输入的字符串，`referenceStage`/`ruleOrderStage` 的 issue **只携带路径、规则序号、
  规则类型与实体名**，不得把整条规则行或 payload 塞进 `messageParams`。每类新 issue
  都要有一条「不回显规则 payload」的否定用例。
- 跨字段规则 DSL 沿用 `condition.ts` 的封闭算子集合，**不引入正则算子**（NFR-SEC-05）。
- `packages/test-fixtures/fixtures/**` 是字节敏感的 golden 文件：**只新增，不修改，
  不格式化**。`.prettierignore` 与 `.gitattributes` 已覆盖整个目录，无需改动。
- 新增架构决策写新 ADR（本版本预计占用 **ADR-021、ADR-022、ADR-023**），
  **不改已 Accepted 的 ADR**。

**实现要点**

- **`buildRulePlan` 不解析规则字符串本身**——解析已由
  `config-model/src/rule-line.ts` 的 `parseRuleLine` 完成（14 例测试，含子片段偏移
  定位）。本片只做「片段 → 目录条目」的对齐与语义标注，**不重复实现解析**。
- **目录条目是数据**：`{ type, payloadKind, needsTarget, params[], docsUrl, since?,
safety }`。`payloadKind` 是封闭枚举（`domain` / `domain-suffix` / `ipcidr` /
  `port` / `process` / `geo` / `rule-set` / `sub-rule` / `none`），控件按它选，
  **不按类型名 switch**——加一种新规则类型只需在 `rule-types.json` 加一行。
  `builtin.test.ts` 要有一条「加第 N+1 种合成规则类型，`schema-core`/`form-renderer`/
  `apps/web` 零改动」的用例，与 v0.3.0 #10 的第十种协议用例同一手法。
- **认不出的类型必须保留为原始字符串**（FR-RULE-05）：`buildRulePlan` 对目录里没有的
  类型返回 `{ kind: 'raw', text }`，而不是抛错、更不是丢弃。这是本片的核心断言，
  与「未知字段不丢」是同一条保真承诺的规则侧入口。
- `rules` 与 `sub-rules` 用**两个**模块而不是一个：`manifest.root` 分别是 `['rules']`
  与 `['sub-rules']`，形状不同（数组 vs `name → 数组`），合并只会让消费方多一层分支。
- `MAX_NESTING` 对逻辑规则（`NOT`/`AND`/`OR` 的括号嵌套）同样生效，恶意规则行不能把
  目录对齐器打爆——但本版本**不解析**逻辑规则内部结构（Out of scope），它们直接走
  `{ kind: 'raw' }`。
- ADR-021 记录：为什么规则行不是 JSON Schema 能表达的形状、目录条目的封闭
  `payloadKind` 枚举、这是 ADR-002 的 Level 2 变更、以及「认不出就保留原文」的保真承诺。

**执行时决策与修正**

- 目录条目字段名 `needsTarget` 改为 `needsPayload`：`config-model/src/rule-line.ts`
  的既有不变量是「本应用触及的 `rules:`/`sub-rules:` 上下文里 target 恒必需」，
  目录里真正变化的维度是「是否需要 payload」（仅 `MATCH`、`SUB-RULE` 可以只有裸
  target）——`needsTarget` 会是个永远为 `true` 的死字段，`needsPayload` 才对应
  真实差异。详见 ADR-021。
- FR-RULE-05 记 **Partial** 而非计划原文的 Done：PRD 原文是「规则**编辑器**必须
  保留无法解析的规则为原始文本」，本片只交付数据层保证
  （`buildRulePlan` 返回 `{kind:'raw'}`），编辑器 UI 是 #8 的范围——在 UI 存在前
  标 Done 会指向一个用户还摸不到的能力，如实记 Partial 并写明缺口（UI 入口见 #8）
  更符合「标 Done 必须能指向具体测试文件」的口径。
- 顺带修复 `packages/validator/src/pipeline.ts` 的 `schemaStage`
  两处既有（v0.3.0 #12 起就存在、本片实现时才因万级规则数组而暴露到无法忽略）
  未知字段假阳性：标量数组字段的每个元素、字典型字段（`additionalProperties`

### #8 规则编辑器：结构化创建与原始字符串保真

**目标**：能用结构化控件创建/编辑一条规则，认不出的规则原样保留为可编辑文本。

**覆盖**：FR-RULE-01、FR-RULE-05。

**依赖**：#7。

**涉及文件**

- 新建：`apps/web/src/rules/RuleEditor.tsx` + `.css` + `.test.tsx`
- 修改：`apps/web/src/rules/RuleListPage.tsx`（接入编辑器）
- 修改：`apps/web/src/i18n/{zh-CN,en}.json`

**实现要点**

- 控件按 #3 的 `payloadKind` 选，**不出现任何规则类型名的 switch**。用例要直接断言
  这一点：给一个合成的、目录里新加的类型（`payloadKind: 'domain'`），编辑器无改动即可用。
- `RULE-SET` 与 `SUB-RULE` 的 payload 是**实体引用**：payload 控件应给出已存在的
  rule-provider / sub-rule 名称的选择项（数据来自 `EntityRegistry`，通过 Worker 的
  `value()` 已有通道拿文档，不新增协议消息）。选不到也允许自由输入——缺失引用由
  #4 报，不在编辑器里硬拦。
- 写回走既有 `applyPatch({ kind: 'set', path: ['rules', i], value: 新字符串 })`
  ——一条规则就是一个字符串标量，**不需要新协议消息**。
- `{ kind: 'raw' }` 的规则渲染成单行只读文本 + 「按原始文本编辑」入口，编辑后仍按
  字符串整体写回。**绝不因为解析不出结构就禁用编辑或丢弃内容**。
- 新建规则默认插在当前选中行之后；`rules` 段整段不存在时先 `set` 出空数组再 `append`。

**执行时决策与修正**

- **新建规则不实现「插在当前选中行之后」，改为整段追加到末尾**：本片没有
  `move`/reorder 能力（要到 #9 才新增 `applyPatch` 的 `{kind:'move'}` 分支），
  唯一能模拟「插入中间」的办法是先 `append` 到末尾、再对中间每个元素依次
  `set` 搬位——那是每次创建规则都要打好几个独立 `applyPatch` 往返、留下好几条
  撤销记录，为了模拟一个 #9 马上就会正确支持的能力而制造一次糟糕的撤销体验，
  不值得。改为始终追加到末尾；用户创建后可以立即用 #9 的拖拽/键盘重排移到
  想要的位置。
- **`rules` 段不存在或为空数组时，不走计划原文的「先 `set` 出空数组再
  `append`」两步，改成一次 `set` 写入含新规则的完整一元数组**：两步版本在真实
  Worker 上稳定复现 `YAML_INVALID_OPERATION`——根因是
  `MihomoYamlDocument#setIn`（`yaml-engine/src/document.ts`）只是把拿到的值
  原样存进 `Pair`（`yaml` 库 `Collection#set` 的行为，没有调用
  `createNode`），所以刚 `set` 出来的 `[]` 是一个普通 JS 数组，不是
  `YAMLSeq`；`appendIn` 自己的 `isSeq` 检查因此拒绝它。改成一次 `set` 写入
  `[新规则文本]` 完全绕开这个组合——`append` 只用在数组已经来自真实解析出的
  `YAMLSeq`（即 `rules` 非空）的场景，那条路径没有这个问题。这是

### #9 拖拽排序与等价键盘路径

**目标**：规则可拖拽排序，且**有完全等价的键盘操作路径**，序号全程可见。

**覆盖**：FR-RULE-02；NFR-A11Y（PRD §11.6「拖拽操作需要键盘替代」）；退出条件 3。

**依赖**：#7。

**涉及文件**

- 修改：`apps/web/src/rules/RuleListPage.tsx`（拖拽 + 键盘重排）
- 新建：`apps/web/src/rules/reorder.ts` + `reorder.test.ts`（纯函数：给定当前索引与
  操作，算出目标索引；含首尾边界与多选区间）
- 修改：`apps/web/src/i18n/{zh-CN,en}.json`

**实现要点**

- **键盘路径不是「也能做到」，是等价**：选中一行后 `Alt+↑/↓` 上下移一位、
  `Alt+Home/End` 移到首尾，每次移动后用 `aria-live="polite"` 播报「已移动到第 N 条」。
  用例要断言：同一组操作，键盘路径与拖拽路径产出**逐字节相同**的文档文本。
- 写回走既有 `document.moveSeqItem(path, from, to)`（`yaml-engine` 已实现并测过
  不丢项）——但目前 Worker 协议**没有** move 消息。本片新增 `applyPatch` 的
  `{ kind: 'move', path, from, to }` 分支（`IssueFix` 联合加一个成员），
  比新增一条协议消息更小；批量移动留给 #10 的 `applyBatch`。
- 拖拽过程中序号持续可见（PRD §7.3 对 Android 的明确要求，桌面同样适用）：
  拖拽中的占位行也显示它**将会**落到的序号，而不是隐藏序号或显示旧序号。
- 拖拽实现用原生 HTML5 drag events，不引依赖（E2）。jsdom 对 drag events 支持有限
  ——**核心断言放在 `reorder.ts` 的纯函数与键盘路径上**，拖拽只测事件处理器被正确
  接线，不假装 jsdom 能验证真实拖拽手感。这条口径要写进测试文件注释。

**执行时决策与修正**

- **`reorder.ts` 的函数签名是索引到索引，不是区间到区间**：计划原文「含首尾边界
  与多选区间」里的「多选区间」没有采用字面的多选 UI 解读——`给定当前索引与操作，
算出目标索引`这句本身就是单数索引进单数索引出，键盘路径的说明通篇也只提「选中
  一行」，且 `document.moveSeqItem` 本身一次只搬一条。真正的多条目批量操作是
  ADR-023／#10「批量操作单次撤销」的范围（如果 #9 就用多次独立 `move` 模拟批量
  移动，会重演 #8 已经决定不做的「多次 `applyPatch` 往返、多条撤销记录模拟一个
  单一操作」的反模式）。`reorder.test.ts` 因此把「多选区间」落实成：横跨整个合法
  索引范围（首、中、尾、越界防御、连续步进不越界）的边界测试矩阵，而不是新增
  选区数据结构。
- **选中状态新增在 `RuleListPage` 内部（`selectedIndex`），键盘事件监听挂在
  `grid` 容器而不是每一行**：虚拟化下行会随滚动挂载/卸载，逐行绑定键盘监听会在

### #10 Worker `applyBatch` 与批量操作单次撤销（ADR-023）

**目标**：批量选择、移动、复制、删除、目标策略替换，**整批一次 undo 回退**。

**覆盖**：FR-RULE-03；退出条件 4。

**依赖**：#9。

**涉及文件**

- 修改：`apps/web/src/worker/protocol.ts`（`ApplyBatchRequest`/`Response`、
  `handleApplyBatch`）、`client.ts`、`protocol.test.ts`、`client.test.ts`
- 修改：`apps/web/src/rules/RuleListPage.tsx`（多选 + 批量动作条）
- 新建：`docs/adr/ADR-023-atomic-batch-edit.md`；修改 `docs/adr/README.md`

**实现要点**

- **一批补丁 = 一次 `historyStack.record()`**。`handleApplyBatch` 把整个
  `IssueFix[]` 的应用包在单个 `record(document, description, () => { for … })` 里，
  `mergeKey` 传 `undefined`（批量操作**绝不**与相邻编辑合并——合并会让「一次 undo
  回退整批」变成「回退整批加上别的东西」）。
- **全成功或全不改**：`record()` 内部任一补丁抛错时，捕获后把文档恢复到调用前文本
  再重新抛出，不留半成品。这是本片的核心断言（3 条补丁，第 2 条非法 → 导出文本与
  调用前逐字节相等，且历史栈长度不变）。
- 五类批量动作的补丁构造都是**纯函数**（在 `apps/web/src/rules/batch.ts`），
  可独立测：移动用 `move`、复制用 `append` + `move`、删除用逆序 `remove`
  （正序删会让后面的下标全部漂移——这是最容易出的错，要有专门用例）、
  目标策略替换用 `set`。
- 退出条件 4 的核心断言写在应用层：真实选中 3 条规则 → 批量替换目标 → 一次 undo →
  导出文本与操作前**逐字节相等**；再 redo → 与操作后逐字节相等。
- ADR-023 记录：为什么不用「逐条 applyPatch + 历史项合并窗口」（合并窗口是时间驱动
  的启发式，语义上不等于原子批次）、全成功或全不改的语义、以及与既有 `mergeKey`
  机制的关系。

**执行时决策与修正**

- **多选 UI 用逐行 checkbox，不做 shift-click 区间选择**：计划原文「多选 + 批量
  动作条」没有规定具体交互方式。Checkbox 是最直接、无歧义的多选机制，且已经
  足以覆盖退出条件 4「选中 3 条规则」的字面场景；shift-click 区间选择是常见但
  计划未明确要求的增强，判断为可以留到真正有需要时再加，不预先构建。
- **批量移动只做「整块上移/下移一步」，不做拖拽任意位置**：单行拖拽到任意位置是
  #9 已经交付的能力（对单选而言，勾选一行再用批量移动等价于单行操作）；对
  多选，"拖拽一整块规则到任意位置" 是明显更复杂的交互（虚拟化下如何展示一整块
  被拖拽的占位、如何处理块内原始相对顺序），计划本身也没有要求这一点——
  「移动用 `move`」的实现要点只提了下标运算，没有要求批量拖拽 UI。批量移动的
  纯函数（`buildBatchMovePatches`）证明了一个优雅性质：不管选中多少行，整块
  上移/下移一步只需要**一次** `move`（把选区外紧邻的一行搬过整个选区），这个
  结果本身就值得先落地，任意位置的批量拖拽留给真正有需求时再评估。
- **批量替换目标对认不出的类型和 `SUB-RULE` 静默跳过，不报错也不阻塞其余行**：
  这是 #8 已经确立的「结构认不出就不猜」原则的批量版本延伸——一批规则里混了
  几条这类规则时，用户的合理预期是「能处理的都处理了，处理不了的保持原样」，
  而不是整批失败或者把 `SUB-RULE` 的组名错误覆盖成一个策略名字。
- **`ModuleFormWorkerClient` 与 `ProjectPage.tsx` 的 `applyFixAndRefresh` 重构为

  共用函数相比是纯粹的重复——抽取是这个诉求下更小的改动，不是范围外的重构。

  正确改写，未勾选的两条原样保留；点击一次「撤销」同时把两条规则都还原

**实现期间的执行时决策与修正（在上面「范围扩大」确认之后）**

- **`analyzeImpact` 协议消息按实体的「条目自身路径」识别，兼容两种
  `sourcePath` 形状**：`SchemaArrayForm` 的 `field.path`（`onDeleteEntry`
  拿到的路径）对数组形态实体（`proxy`/`proxy-group`）是条目本身的路径
  （如 `['proxy-groups', 0]`），比 `Entity.sourcePath`（`[key, index,
'name']`）短一段；对字典形态实体（`proxy-provider`/`rule-provider`）
  两者恰好相等（`[key, name]`）。Worker 侧 `identifiesEntity()` 同时接受
  「完全相等」与「比 sourcePath 少最后一段」两种匹配，调用方不需要知道
  `EntityRegistry` 内部用的是哪种形状。
- **`buildCascadeDeletePatches` 的排序：先按父容器分组，组内再降序，
  不是一个全局比较器**——第一版用一个「若末段都是数字则比较，否则判等」
  的比较器传给 `Array#sort`，单测（`impact-patches.test.ts`）直接测出
  这个比较器不满足传递性（`proxy-groups[1].proxies[0]` 的末段 `0` 会被
  拿来跟 `proxy-groups[0]`/`proxy-groups[2]` 的末段比较，三者其实分属
  两个不同数组），排序结果随 V8 具体用哪种排序算法而不同、不可靠。改成
  「先按父路径分组，组内按末段降序，组间保持原始相对顺序」，从算法上
  排除了这个问题，不再依赖比较器的传递性假设。这是本片单测在合入真实
  Worker 之前就抓到的一个真实实现 bug，不是事后从真实浏览器测出来的。
- **「替换引用」与「级联删除」不是同一份 `replaceable` 的两种可选动作，
  是两套互斥语义**：读 `impact.ts` 源码确认——`replaceable` 只包含「所属组
  移除该引用后不会变空」的引用；会变空的那些引用本身从不出现在
  `replaceable` 或 `cascading` 里，只有其**所属组**作为一个实体出现在
  `cascading` 里。因此「替换引用」在 `cascading` 非空时是不完整的（无法
  安全处理会变空的那些所属组），对话框据此让 `cascading` 是否为空唯一
  决定出哪一个 UI，不是由调用方传参决定。「级联删除」路径里，
  `replaceable` 的每条引用没有替换目标可用，只能移除（数组项）或删掉
  整行（标量片段引用——规则不能留一个空 target），这一点计划原文没有
  明确写，是读 `impact.ts` 源码后推导出的必然结论，写清楚在
  `impact-patches.ts` 与 `DeleteImpactDialog.tsx` 的文件头注释里。
- **替换目标候选名单里，`proxy-provider` 这一类返回空数组（自由文本
  仍可用）**：候选名单要读 `documentValue` 的 `proxy-providers` 顶层键，
  但这个键名恰好是 `schema-registry-boundary.test.ts`（FR-SCHEMA-05）
  保护的六个原始模块 id 之一，加引号的字面量在 `apps/web/src` 下不允许
  出现，且这个键名带连字符不能用点号写法绕开（`#8`/`#10` 遇到
  `proxies` 时能用点号写法是因为它没有连字符）。判断为窄范围、可接受的
  功能缺口（少一类自动补全建议，不影响正确性），不去写字符串拼接之类
  的手法绕过检查。
- 真实浏览器复验：无引用直接删除（不弹框）、有引用替换（对话框正确显示
  「有 N 处引用」、替换后引用改写正确、一次撤销完整复原）均通过，过程中
  无 console 报错。级联删除路径复用同一套弹框/写回机制，仅补丁构造不同，
  该差异部分已有单测与真实 Worker 集成测双重覆盖，未额外在浏览器里手动
  复验。

### #12 关系图数据层：聚合、异常关系与分层布局

**目标**：把 `packages/graph` 的引用索引变成一份**可直接绘制**的分层图数据，
并在 1,000 实体下仍然可读。

**覆盖**：FR-REL-04（数据侧）；FR-REL-06 的筛选数据基础。

**依赖**：#4。

**涉及文件**

- 新建：`packages/graph/src/layout.ts` + `layout.test.ts`
- 修改：`packages/graph/src/index.ts`（导出）

**实现要点**

- **分层固定为三层**：节点/Provider → 代理组 → 规则。这是 PRD §8.5 FR-REL-04 的
  原文结构，不需要通用图布局算法（E2）。层内顺序按名称稳定排序，保证同一文档两次
  布局结果**完全相同**（可断言，也让 UI 的 diff 稳定）。
- **默认聚合视图**（版本文档风险表的缓解措施）：同一层内超过 N 个同构节点时折叠成
  一个「N 个节点」的聚合节点，展开是 UI 的事，聚合判定是数据层的事。N 走参数，
  有默认值，不写死在 UI 里。
- **异常关系标记**：每条边带 `status: 'ok' | 'missing' | 'cycle'`。`missing`/`cycle`
  的判定**复用 #4 的 `referenceStage` 结论**（同一份 issue 列表），不在这里第二次
  实现引用解析——两处独立实现必然漂移。签名上接受 `readonly ValidationIssue[]`。
  这会让 `packages/graph` 依赖 `@mcs/validator`；若产生循环依赖（validator 已依赖
  graph），改为接受一个窄接口 `{ path, code }[]`，由调用方传入，graph 不 import
  validator。**实现时先验证依赖方向，选后者更安全。**
- 纯函数、无 DOM、无计时器，在 node 环境测；1,000 实体的布局有一条耗时上界断言。
- NFR-SEC-03：节点只带实体名与 kind，不带任何字段值。

**执行时决策与修正**

- **依赖方向按计划要求先验证，确认必须用窄接口**：`@mcs/validator` 已经
  `import { detectCycles } from '@mcs/graph'`，如果 `layout.ts` 反过来
  `import type { ValidationIssue } from '@mcs/validator'` 会立刻形成循环
  依赖。`RelevantIssue`（`{code, path?, messageParams?: {cycle?}}`）是按
  这个约束设计的窄接口——`path` 与 `Reference.path` 同址（都指向引用发起
  side），`messageParams.cycle` 与 `detectCycles()` 返回的 `Cycle`（名字
  序列，首尾相等）同构，调用方（validator 产出的 issue 或未来的 UI）自己
  按这个形状适配，`graph` 包本身不知道 `ValidationIssue` 这个类型存在。
- **`ReferenceIndex` 新增 `allReferences()`**：不在计划文件清单里，但
  `layout.ts` 需要文档里*全部*的边，而 `ReferenceIndex` 原来只有按目标
  查询的 `referencesTo(entityId)`——重新扫描文档算一遍边是对已有能力的
  重复实现（`collectReferences` 已经是私有的、不该在 `layout.ts` 里重新
  写一遍），直接把 `ReferenceIndex` 内部已经算好的 `#referencesToId` 摊平
  导出一个新方法比复制逻辑更小、更不容易和原实现漂移。
- **三层里 `rule-provider`/`sub-rule`/`builtin` 三种 kind 的归层是自决的，
  不是计划原文直接给的**：计划原文「节点/Provider → 代理组 → 规则」只
  点名了 3 个概念层，但 `EntityKind` 有 7 种。按角色而不是字面词归类：
  `builtin`（DIRECT/REJECT 等最终出站目标）和 `proxy`/`proxy-provider`
  一起算「节点/Provider」层（都是流量最终去向）；`rule-provider`/
  `sub-rule` 和 `rule` 一起算「规则」层（都是决定匹配到哪条策略的东西）。
  这是判断上最贴近三层各自「概念角色」（出站目标 / 选择分组 / 匹配决策）
  的分法，写清楚在 `layout.ts` 的 `LAYER_KINDS` 常量旁。
- **聚合去重的严重度合并策略**：同一对 `(fromId, toId)` 在聚合折叠后可能
  被多条原始引用同时命中，若它们状态不同（理论上 `missing`/`cycle` 不会
  和对方同时出现在同一条引用上，因为不存在的目标不可能参与环检测），
  保留态取「非 ok 优先于 ok」，不会让后来的一条 `ok` 边覆盖掉先记录的
  `missing`/`cycle`。

- **计划原文「六个阶段全跑」的口径修正**：`packages/validator/src/pipeline.ts` 的

  <1ms）——这不是放宽阈值，是把测量对象改回 NFR-PERF-03 本来就要求排除的
  「Worker 异步往返」之外。这个假 Worker 写法的缺陷可能同样存在于其它
  以 v0.3.0 该文件为模板的未来性能测试里，值得在写新的这类测试时留意。
