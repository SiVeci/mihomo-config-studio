## 上游事实（本轮实测，2026-08-25）

### `rule-providers` 的 `format: mrs` 对 `behavior` 的取值约束 —— 先决项，**已核实**

依据是仓库内已 vendor 的 v1.19.29 官方 `docs/config.yaml`
（`packages/test-fixtures/fixtures/upstream/mihomo-v1.19.29/config.yaml`，
tag `v1.19.29`、commit `e26714a1`、blob `0598d098`，见 `SOURCE.md`）。逐行核对结果：

| 行            | 原文要点                                                                                           |
| ------------- | -------------------------------------------------------------------------------------------------- |
| 1860          | 「mrs类型ruleset，目前仅支持domain和ipcidr(即不支持classical）」                                   |
| 1862–1870     | `behavior=domain` 与 `behavior=ipcidr` 各自的 `format=yaml`/`format=text` → mrs 转换               |
| 1872–1876     | 唯一的 `format: mrs` 实例：`type: http` + `format: mrs` + `behavior: domain`                       |
| 1847/1855     | `behavior: classical` 实例，均**不带** `format`（默认 yaml）                                       |
| 1880          | `type: inline` 的 `behavior: domain # classical / ipcidr`                                          |
| 272–273 / 365 | 另一条约束：被 `fake-ip-filter` / DNS fallback 引用的 RULE-SET，`behavior` 必须是 domain/classical |

**结论**：`format: mrs` ⇒ `behavior ∈ {domain, ipcidr}`，`classical` 被明确排除。
与 PRD §8.3「规则集合」P0 范围「Classical/Domain/IPCIDR、YAML/Text/MRS」**不构成矛盾**
——PRD 列的是各维度的取值集合，没有声称三×三全组合合法。故**不新增 D-xxx 差异记录**，
只在 `upstream-divergences.md` 的「待核对项」表把该行从「待核对」改为「已关闭」并写明依据
与日期（#0）。

**证据分级，如实记录**：本条是**文档级证实**（钉死版本自带的官方示例配置 + 官方
Meta-Docs 源码），不是**内核级实测**。内核级实测的落点是 #17 —— 「规则集合分流配置」
模板会包含一条 `format: mrs` + `behavior: domain` 的 `rule-providers` 条目，由 CI 的
`core-config-test` job 用真实 `mihomo -t` 跑过（该 job 的运行方式见决策 E8：推分支到
`origin` 触发 CI，本机不执行外部二进制）。

**交叉核对已于执行阶段补齐（#0，2026-08-25）**：编制阶段用 `WebFetch` 拉取
`raw.githubusercontent.com/MetaCubeX/Meta-Docs/.../rule-providers/index.md` 做第二来源
交叉核对被本环境的网络策略拒绝（"Unable to verify if domain ... is safe to fetch"）；
执行 #0 时改用 `gh api repos/MetaCubeX/Meta-Docs/contents/...`（GitHub API，走 `gh` CLI
而非 `WebFetch` 工具）成功拉取，原文「mrs目前 behavior 仅支持 domain/ipcidr」与 vendor

## 本轮确认的决策

这些是编制期已判定、实现时必须遵守的口径。**不需要你逐条确认**，但会体现在对应 ADR 里。

| 编号 | 决策                                                                                                                                                                                                                                                                                                                                                                                |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| E1   | **`rules`/`sub-rules` 走声明式「规则类型目录」，不走 JSON Schema 表单**。目录是 Bundle 数据（`schema-builtin/modules/rules/rule-types.json`），描述每种规则类型的 payload 形态、是否需要 target、参数与文档链接。新增一种规则类型只改数据、不改应用代码——FR-SCHEMA-06 的同一条性质在规则侧成立。需要扩 `SchemaModule`（ADR-002 Level 2）。写 **ADR-021**                            |
| E2   | **虚拟化与关系图一律自建，不引入任何新的运行时依赖**（不引 react-window / @tanstack/virtual / d3 / elkjs / cytoscape）。理由与既有先例一致：自建 hash router、自建 i18n、零依赖手写 ZIP（ADR-018）；离线优先（NFR-SEC-01/退出条件「离线可运行」）与 Android WebView 体积都不欢迎新依赖；关系图只需要**分层 DAG**（节点/Provider → 组 → 规则），不需要通用图布局引擎。写 **ADR-022** |
| E3   | **主列新增「表单 / 规则 / 关系图」视图切换，用组件内 state，不新增路由**。依据 PRD §7.2「中间：图形化表单、列表、拖拽排序和关系图」与 §7.3 Android 底部导航「配置、关系、YAML、问题」。副产品是惰性挂载——10,000 条规则的列表与关系图不会在用户没看它们时被渲染。`router.tsx` 的「路由数是否超出精确匹配」注释按此判定更新为「未超出」                                               |
| E4   | **批量操作走新的 Worker 消息 `applyBatch`，一批补丁包在**一次** `HistoryStack.record()` 里**。既有 `applyPatch` 是单补丁，逐条发送必然产出多条历史项，直接违反退出条件 4。`applyBatch` 语义为全成功或全不改（任一补丁抛错则整批回滚到调用前文本），失败不留半成品。写 **ADR-023**                                                                                                   |
| E5   | **不扩 `detectCycles` 的边类型**。版本文档退出条件 6 只要求「循环引用被阻断并能展示环路路径」，既有两类边（proxy-groups 嵌套、dialer-proxy）已覆盖 PRD §8.5 FR-REL-05 的验收要点。#4 只把 `detectCycles` 的结果接进流水线并置为 `blocking: true`，#13 把 `Cycle`（名称序列）画在图上。`rule-providers` 不构成引用环（规则集合不引用规则集合），无需新边                             |
| E6   | **FR-RULE-04 的四类检查一律 `severity: 'warning'`、`blocking: false`**，与 v0.3.0 #13 的 `securityStage` 同一口径：静态分析不得声称与内核运行时等价（PRD §8.6 末句、NG-07），一条不能保证等价的判断没有资格阻断导出。唯一例外是「缺失 RULE-SET / 缺失策略」——那是**引用完整性**问题，归 #4 的 `referenceStage`，按缺失引用的既有口径判 `error` 且阻断                               |
| E7   | **「明显遮蔽」宁可漏报不可误报**（版本文档风险表原话）。只检测**同类型、同 target 语义下的真包含**（如 `DOMAIN-SUFFIX,a.com` 在前、`DOMAIN,x.a.com` 在后且 target 不同），不做跨类型推理、不做 GEO/RULE-SET 内容展开（内容在远端文件里，本工具从不抓取——ADR-005）。检测不到就不报                                                                                                   |
| E8   | **内核测试走 CI，本机不下载也不执行内核二进制**（2026-08-25 答复 Q1）。切片分支 push 到 `origin` 触发 `core-config-test` job；**#0 完成后立刻首推**，让另外四个 job 也第一次真实验证。退出条件 7 的证据 = 该 job 的 run URL + 五个模板各自的 `mihomo -t` 退出码。详见「待你确认的问题」下的 E8 小节                                                                                 |
| E9   | **「Android 生成目标配置」是普通 Mihomo YAML，不引入平台专属产物格式**（2026-08-25 答复 Q2）。以 `tun` 为核心 + `platforms: ["android"]`；追踪表 §8.8 那句「依赖尚未设计的平台专属产物格式」与代码现状不符，由 #17 一并改掉。详见 E9 小节                                                                                                                                           |

## 工程约束（每片实现时都适用）

- Node ≥ 20.11 / pnpm 10。验收 = `pnpm run check`（typecheck + lint + test）**和**
  `pnpm run format:check`。后者在 CI 是独立步骤，**最容易漏**。
- 覆盖率阈值（行 / 函数 / 语句 85、分支 80）在 `vitest.config.ts` 强制，**不得放宽**。
  新增文件落在既有 `packages/*/src/**`、`apps/web/src/**` glob 内，自动纳入统计。
- 追踪表口径：**标 Done 必须能指向具体测试文件**，否则记 Partial 并写明缺口。
- `packages/**` 禁止 `node:fs`（ESLint `no-restricted-imports`）与任何网络调用
  （CI `no-network-egress` job 用 grep 拦 `fetch|XMLHttpRequest|WebSocket|sendBeacon`）。
  **本版本的直接后果**：新模块的 `examples/*.yaml`、`rule-types.json` 不能在运行时读盘，
  由 `import ... with { type: 'json' }` 或测试文件读取；关系图与规则编辑器**绝不因为
  要「解析 RULE-SET 内容」而发起任何请求**（ADR-005）。
- 工作区内部包直接导出 TypeScript 源码（ADR-007）：`exports` 指向 `./src/index.ts`。
- 用户可见文本一律 i18n key，不写字面量（ADR-016）。中英资源文件 key 集合必须相等，
  由 `apps/web/src/i18n/i18n.test.ts` 的双向差集断言强制；模块自带 `i18n/*.json` 同理。
- 错误与日志消息不得包含配置值（NFR-SEC-03）。**本版本高危面**：规则行本身就是用户
  输入的字符串，`referenceStage`/`ruleOrderStage` 的 issue **只携带路径、规则序号、
  规则类型与实体名**，不得把整条规则行或 payload 塞进 `messageParams`。每类新 issue
  都要有一条「不回显规则 payload」的否定用例。
- 跨字段规则 DSL 沿用 `condition.ts` 的封闭算子集合，**不引入正则算子**（NFR-SEC-05）。
- `packages/test-fixtures/fixtures/**` 是字节敏感的 golden 文件：**只新增，不修改，
  不格式化**。`.prettierignore` 与 `.gitattributes` 已覆盖整个目录，无需改动。
- 新增架构决策写新 ADR（本版本预计占用 **ADR-021、ADR-022、ADR-023**），
  **不改已 Accepted 的 ADR**。
- PRD / ADR 与上游实际行为冲突时以上游为准，记入 `docs/upstream-divergences.md`，
  不得静默改需求。本版本目前**无**新增 D-xxx（`mrs`/`behavior` 不构成差异，见上）。
- 分支名 `feat/v0.4.0-<切片名>`，从 `main` 切出，**不在 main 上直接提交**；提交信息用中文。

### #3 规则类型目录与 `rules`/`sub-rules` 模块契约（ADR-021）

**目标**：让「一条规则行」有一个声明式、可由 Bundle 更新的类型目录，`rules` 与
`sub-rules` 成为第九、第十个内置模块，而不被硬塞进 JSON Schema 表单机制。

**覆盖**：PRD §8.3「路由规则」「子规则」P0；FR-RULE-01/05 的数据基础；FR-SCHEMA-06。

**依赖**：#0。

**涉及文件**

- 修改：`packages/schema-core/src/types.ts`（`SchemaModule` 加可选 `ruleTypes?`；
  新增 `RuleTypeSpec` 类型）
- 修改：`packages/schema-core/src/module.ts`（`validateModuleShape` 覆盖新字段）
- 新建：`packages/schema-core/src/rule-catalog.ts` + `rule-catalog.test.ts`
  （`buildRulePlan(catalog, rawLine)`：把 `parseRuleLine` 的片段与目录条目对上，
  产出可渲染的「类型 / payload / target / 参数」结构；认不出的类型退回原始字符串）
- 新建：`packages/schema-builtin/modules/rules/{module.manifest.json,rule-types.json,
i18n/*.json,examples/*.yaml}` 与 `modules/sub-rules/{...}`
- 修改：`packages/schema-builtin/src/index.ts`、`builtin.test.ts`
- 修改：`packages/schema-registry/src/builtin.ts`（重签）
- 新建：`docs/adr/ADR-021-declarative-rule-type-catalog.md`；修改 `docs/adr/README.md`

**实现要点**

- **`buildRulePlan` 不解析规则字符串本身**——解析已由
  `config-model/src/rule-line.ts` 的 `parseRuleLine` 完成（14 例测试，含子片段偏移
  定位）。本片只做「片段 → 目录条目」的对齐与语义标注，**不重复实现解析**。
- **目录条目是数据**：`{ type, payloadKind, needsTarget, params[], docsUrl, since?,
safety }`。`payloadKind` 是封闭枚举（`domain` / `domain-suffix` / `ipcidr` /
  `port` / `process` / `geo` / `rule-set` / `sub-rule` / `none`），控件按它选，
  **不按类型名 switch**——加一种新规则类型只需在 `rule-types.json` 加一行。
  `builtin.test.ts` 要有一条「加第 N+1 种合成规则类型，`schema-core`/`form-renderer`/
  `apps/web` 零改动」的用例，与 v0.3.0 #10 的第十种协议用例同一手法。
- **认不出的类型必须保留为原始字符串**（FR-RULE-05）：`buildRulePlan` 对目录里没有的
  类型返回 `{ kind: 'raw', text }`，而不是抛错、更不是丢弃。这是本片的核心断言，
  与「未知字段不丢」是同一条保真承诺的规则侧入口。
- `rules` 与 `sub-rules` 用**两个**模块而不是一个：`manifest.root` 分别是 `['rules']`
  与 `['sub-rules']`，形状不同（数组 vs `name → 数组`），合并只会让消费方多一层分支。
- `MAX_NESTING` 对逻辑规则（`NOT`/`AND`/`OR` 的括号嵌套）同样生效，恶意规则行不能把
  目录对齐器打爆——但本版本**不解析**逻辑规则内部结构（Out of scope），它们直接走
  `{ kind: 'raw' }`。
- ADR-021 记录：为什么规则行不是 JSON Schema 能表达的形状、目录条目的封闭
  `payloadKind` 枚举、这是 ADR-002 的 Level 2 变更、以及「认不出就保留原文」的保真承诺。

**执行时决策与修正**

- 目录条目字段名 `needsTarget` 改为 `needsPayload`：`config-model/src/rule-line.ts`
  的既有不变量是「本应用触及的 `rules:`/`sub-rules:` 上下文里 target 恒必需」，
  目录里真正变化的维度是「是否需要 payload」（仅 `MATCH`、`SUB-RULE` 可以只有裸
  target）——`needsTarget` 会是个永远为 `true` 的死字段，`needsPayload` 才对应
  真实差异。详见 ADR-021。
- FR-RULE-05 记 **Partial** 而非计划原文的 Done：PRD 原文是「规则**编辑器**必须
  保留无法解析的规则为原始文本」，本片只交付数据层保证
  （`buildRulePlan` 返回 `{kind:'raw'}`），编辑器 UI 是 #8 的范围——在 UI 存在前
  标 Done 会指向一个用户还摸不到的能力，如实记 Partial 并写明缺口（UI 入口见 #8）
  更符合「标 Done 必须能指向具体测试文件」的口径。
- 顺带修复 `packages/validator/src/pipeline.ts` 的 `schemaStage`
  两处既有（v0.3.0 #12 起就存在、本片实现时才因万级规则数组而暴露到无法忽略）
  未知字段假阳性：标量数组字段的每个元素、字典型字段（`additionalProperties`
  无命名 `properties`）的每个键，此前都会被判定为 `unknown-field`。不是计划列出
  的文件，但不修的话 `rules:` 一旦有真实内容就会在问题面板里产生数以千计的
  噪音——与本版本 NFR-PERF-04 的核心诉求直接冲突，判断为必须现在处理而非留给
  #4/#5/#7 各自绕过。详见 ADR-021「副产品」一节与 `pipeline.test.ts` 的两条回归
  用例。

**验收命令**

```bash
pnpm run check && pnpm run format:check
```

**完成后更新的文档行**：追踪表 §8.3 新增「路由规则」「子规则」两行 → Done（数据层，

### #5 validator 阶段 5：规则顺序与明显遮蔽（FR-RULE-04）

**目标**：接上 PRD §8.7 流水线第 5 级——MATCH 位置与明显遮蔽。

**覆盖**：FR-RULE-04（顺序侧；缺失策略/缺失 RULE-SET 归 #4，见 E6）。

**依赖**：#3、#4。

**涉及文件**

- 新建：`packages/validator/src/rule-order.ts` + `rule-order.test.ts`
- 修改：`packages/validator/src/pipeline.ts`（`DEFAULT_STAGES` 追加）、`index.ts`

**实现要点**

- **MATCH 位置**：`MATCH` 之后还有规则 → `warning`，携带规则序号；`rules` 非空但
  完全没有 `MATCH` → `warning`（上游会落到默认行为，不是解析失败）。均不阻断（E6）。
- **明显遮蔽**：只做真包含判定（E7）。检测集合限定在**同一 payloadKind 家族内**：
  `DOMAIN-SUFFIX` 遮蔽后面的 `DOMAIN`/`DOMAIN-SUFFIX`；`IP-CIDR` 遮蔽后面被其网段
  包含的 `IP-CIDR`。target 相同则不报（那只是冗余，不是行为差异）。
  **不展开 GEO / RULE-SET**（内容在远端，本工具从不抓取）、**不跨类型推理**、
  **不对正则类规则做任何包含判断**（NFR-SEC-05：不对用户提供的正则求值）。
- **复杂度**：朴素两两比较在 10,000 条规则上是 5×10⁷ 次——不可接受。按
  payloadKind 分桶 + 桶内按后缀/网段前缀排序后单次线性扫描。这一条是 #14 基准的
  直接约束对象。
- 所有提示文案的 i18n key 在本片起草，**措辞审查在 #18** 统一做。
- NFR-SEC-03：issue 只带规则**序号**、类型名与 payloadKind，**不带 payload 原文**。
  一条否定用例用真实域名/IP 断言序列化后的 issue 不含该字符串。

**执行时发现（记录给 #14/#15，不在本片处理）**：在 1MB/13,106 条规则的真实语料
（`generateLargeCorpus()`）上，遮蔽检测算法本身（分桶 + 哈希查找）隔离测得约
15ms，完全达标；但把检测结果转成 `ValidationIssue`（每条 issue 调一次
`document.locate()`）实测约 1.7s——根因在 `yaml-engine` 的
`MihomoYamlDocument#positionState()`：缓存命中检查本身要先 `toText()`
重新序列化整份文档才能比较，命中与否都已经付出了这个代价。这是**所有**阶段
共享的既有特征（不是本片算法的问题，本片算法已用探针脚本隔离验证），只是
本片第一次在大语料上产出数以百计的 issue 才把它暴露到无法忽略。已在
`rule-order.ts`/`bench/corpus.test.ts` 留下指向 #14/#15 的注释，`bench/corpus.test.ts`
的语料 sanity 用例超时从默认 5s 提到 10s（真实耗时，不是放宽断言）。#15 的
"排序期间挂起全量校验"备用手段之外，这条也是 #15 判断是否需要优化时的直接输入。

### #10 Worker `applyBatch` 与批量操作单次撤销（ADR-023）

**目标**：批量选择、移动、复制、删除、目标策略替换，**整批一次 undo 回退**。

**覆盖**：FR-RULE-03；退出条件 4。

**依赖**：#9。

**涉及文件**

- 修改：`apps/web/src/worker/protocol.ts`（`ApplyBatchRequest`/`Response`、
  `handleApplyBatch`）、`client.ts`、`protocol.test.ts`、`client.test.ts`
- 修改：`apps/web/src/rules/RuleListPage.tsx`（多选 + 批量动作条）
- 新建：`docs/adr/ADR-023-atomic-batch-edit.md`；修改 `docs/adr/README.md`

**实现要点**

- **一批补丁 = 一次 `historyStack.record()`**。`handleApplyBatch` 把整个
  `IssueFix[]` 的应用包在单个 `record(document, description, () => { for … })` 里，
  `mergeKey` 传 `undefined`（批量操作**绝不**与相邻编辑合并——合并会让「一次 undo
  回退整批」变成「回退整批加上别的东西」）。
- **全成功或全不改**：`record()` 内部任一补丁抛错时，捕获后把文档恢复到调用前文本
  再重新抛出，不留半成品。这是本片的核心断言（3 条补丁，第 2 条非法 → 导出文本与
  调用前逐字节相等，且历史栈长度不变）。
- 五类批量动作的补丁构造都是**纯函数**（在 `apps/web/src/rules/batch.ts`），
  可独立测：移动用 `move`、复制用 `append` + `move`、删除用逆序 `remove`
  （正序删会让后面的下标全部漂移——这是最容易出的错，要有专门用例）、
  目标策略替换用 `set`。
- 退出条件 4 的核心断言写在应用层：真实选中 3 条规则 → 批量替换目标 → 一次 undo →
  导出文本与操作前**逐字节相等**；再 redo → 与操作后逐字节相等。
- ADR-023 记录：为什么不用「逐条 applyPatch + 历史项合并窗口」（合并窗口是时间驱动
  的启发式，语义上不等于原子批次）、全成功或全不改的语义、以及与既有 `mergeKey`
  机制的关系。

**验收命令**

```bash
pnpm run check && pnpm run format:check
```

**完成后更新的文档行**：追踪表 FR-RULE-03 → Done；FR-PROJ-04 证据补上批量操作是
单一历史项；ADR 索引新增 ADR-023。
