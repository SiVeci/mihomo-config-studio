# v0.4.0 性能基线：1,000 实体 + 10,000 规则（NFR-PERF-04，测量侧）

覆盖切片 #14。记录版本文档「测试要求 · 性能」三条要求各自的基准数字：
10,000 条规则的排序（单次 `moveSeqItem` 与 100 次连续移动）、10,000 条规则的批量替换
（一次 `applyBatch` 等效操作替换 1,000 条的 target）、1,000 实体 + 10,000 规则的全量校验
（`runPipeline` 全部五个阶段）。**本片只测量，不优化**——退出条件「列表虚拟化生效、
编辑反馈 < 100 ms」是 #15 的范围，这里记录的是 #15 优化前的起点数字。

**口径限定**：数字来自本机开发环境，不是 CI 标准环境，与
`v0.2.0-perf-baseline.md`/`v0.3.0-perf-baseline.md` 口径一致。

## 复现方法

```bash
pnpm vitest bench --run packages/validator/src/bench/scale.bench.ts
```

四条基准相互独立：排序两条各自持有自己的已解析 `MihomoYamlDocument`（在同一进程内
被反复调用变异，不重新解析——反复对同一份 10,000 行文档做「移动一项」这个操作，
数组大小全程不变，重复调用之间的结构性代价不受累积影响）；批量替换每个样本用一个
全新 `HistoryStack` 包住 1,000 次 `setIn`，与 `apps/web/src/worker/protocol.ts` 的
`handleApplyBatch` 同一模式；全量校验每个样本重新 `MihomoYamlDocument.parse()` 一次
干净语料，独立测量、不含前一样本遗留的状态。

## 关键发现：`schemaStage` 是全量校验的绝对瓶颈

全量校验的 17.2 秒中位数**几乎全部**来自 `schemaStage`——五阶段单独测量
（同一语料，隔离运行）：

| 阶段        | 耗时        | 产出的 issue 数                  |
| ----------- | ----------- | -------------------------------- |
| `syntax`    | 0.1 ms      | 0                                |
| `schema`    | **~40.7 s** | 10,000（全部是 `unknown-field`） |
| `reference` | 30.1 ms     | 0                                |
| `ruleOrder` | 1104.5 ms   | 247                              |
| `security`  | 16.7 ms     | 2                                |

（这次隔离测量比 `scale.bench.ts` 里的全量校验数字更慢——隔离测量单独跑一次
`schemaStage`，没有前面已跑过的其它阶段/其它 bench 带来的 JIT 预热；两次测量的
量级结论一致，`schemaStage` 都是唯二可见的耗时来源，其余四阶段合计不到 1.2 秒。）

**根因判断**：`rules:` 数组的每一条目前都是"未知字段"——`rules`/`sub-rules`
走的是 ADR-021 的声明式规则类型目录，不是逐条目 JSON Schema 校验（`schema-builtin`
的 rules 模块声明的是 `rules:` 这个**键**本身，不是数组**每一项**的形状）——所以
`schemaStage` 对 10,000 条规则里的每一条都产出一个 `unknown-field` issue。这本身
是**已知、如实的行为**（并非 bug——ADR-021 的设计就是规则类型目录而非表单化校验），
但 10,000 个 issue 各自需要把 `path` 解析成编辑器 `range`，命中的正是
`packages/validator/src/bench/corpus.test.ts` 已经记录过的既有 `yaml-engine` 特性：
`MihomoYamlDocument#positionState()` 在缓存命中检查之前先 `toText()` 整份文档
重新序列化一次，每条 issue 一次，与规则条数成正比。v0.4.0 #5 在 13,106 条规则的
旧语料上已经测过 `ruleOrderStage` 的同一现象（365 个 issue，约 1.7 秒）；这次是
10,000 个 `unknown-field` issue 撞上同一瓶颈，数量级放大到近 30 倍。

**这不是 #14 的修复范围**（本片只测量），但是 #15「虚拟化落实与编辑反馈复验」
最直接、优先级最高的优化线索——`ruleOrderStage`/`schemaStage` 都不是各自的
算法慢（`ruleOrderStage` 自己的遮蔽检测隔离测得 <15ms/13k 规则，见 #5 执行记录），
真正的成本集中在"每个 issue 转一次 range"这一步的 `positionState()` 重复
序列化。已知的候选修复方向（留给 #15 判断是否要做、怎么做）：给
`MihomoYamlDocument` 加一个随每次结构性变更递增的版本号，`positionState()`
按版本号比较是否需要重新计算，而不是无条件 `toText()` 后再比较。

## 已知缺口 / 口径说明

- **CI 只记录不阻断**（`.github/workflows/ci.yml` 的 `perf-baseline` job 新增一步
  跑 `scale.bench.ts`，`continue-on-error: true`，不新增 job）：CI runner 比本机更
  慢，全量校验这一项在 CI 上可能明显超过本机的 17 秒中位数，这是预期的，不代表
  回归。
- **全量校验每次进程只 1 个真实样本**：单样本代价（15–18 秒）远超
  `tinybench` 默认的 warmup（5 样本）+ 正式采样（10 样本）预算所能承受的量级——
  按默认值跑，仅这一个 `describe` 块就要接近 15 次完整通过（约 10 分钟）。改为
  `iterations: 1, warmupIterations: 0`，用**跨进程**的 5 次独立调用换取统计意义，
  与前两版基线文档的方法学一致，只是把"多样本"从进程内搬到进程间。5 次独立样本本身
  RME 相当可观（14.7s–18.2s，约 19% 峰谷差），比排序/批量替换两项的类内 RME
  （<3.3%）大得多——这是预期的：单样本天然没有类内平均掉噪声的机会，5 个独立
  样本的离散度直接反映真实的系统噪音（GC、调度、其它进程），而不是测量方法的缺陷。
- **本机、非独占测试环境**：与前两版同样的限制，未特别隔离后台进程、未在最低
  支持版本 Node 20.11 上单独采样。
- **`pnpm vitest bench --run scale.bench.ts` 在系统负载高时可能以非零退出码结束**，
  与本文档记录的数字本身无关：vitest 的 worker↔主进程 RPC（`birpc`，默认 60 秒
  超时）偶发抛出 `[vitest-worker]: Timeout calling "onTaskUpdate"`，即使三个
  `describe` 块都已经跑完并打印出有效数字——全量校验单样本 14–30+ 秒本身就是
  `tinybench`（为大量快样本设计）不擅长的形状，负载叠加后偶发触发。已尝试把该
  基准压到 1 样本、给快基准限制采样数量两类修复，均只降低概率、未根治——
  `birpc` 的超时不经 `vitest.config.ts` 暴露，没有官方配置项可调。确认过这与
  测量数字的正确性无关（失败总是发生在真实结果已经打印**之后**），本文档记录
  的数字来自一次干净通过的运行；`scale.bench.ts` 里 `EXPENSIVE_BENCH_OPTIONS`
  旁留了同样的说明。经与用户确认，这个已知的、偶发的、无害的失败模式按现状
  记录，不作为本片的阻断项。
- **`generateScaleCorpus` 生成的语料不含 `proxy-provider`/`rule-provider` 实体**——
  与既有 `generateLargeCorpus` 同样的简化（那个生成器也不含 provider），"1,000
  实体"全部是 `proxy`/`proxy-group`。如果 #15 或之后的版本需要按实体**类型**细分
  性能画像，这是一个已知的语料简化，不是被忽略的需求缺口。

## v0.4.0 #15 补充：虚拟化复验与编辑反馈达标

< 100 ms，有基准记录」的达标侧验证，测试文件：
`apps/web/src/rules/rule-list-scale.perf.test.tsx`。

### 虚拟化

用 `generateScaleCorpus()` 的真实 10,000 条规则（非合成占位符）渲染
`RuleListPage`，断言渲染出的 DOM 行数量 < 100。机制是 #7 已落地的既有虚拟化
（`packages/ui/src/virtual-list.ts` 的 `computeVirtualWindow()`），本片未改动
`RuleListPage.tsx` 的渲染代码，只是在真实 v0.4.0 语料上重新确认一次。**达标**。

### 编辑反馈（键盘重排，10,000 行规模）

5 次独立进程调用（`pnpm vitest run apps/web/src/rules/rule-list-scale.perf.test.tsx`
各跑一次），每次内 30 个连续 Alt+↓ 键盘重排样本，测「DOM 事件 →
`handleGridKeyDown` → `handleMove` → `onApplyFix` → `client.applyPatch` 同步
派发」这段纯主线程耗时（口径与 v0.3.0 `field-edit-latency.perf.test.tsx` 完全
一致，不含 Worker 异步往返）：

| 指标                            | 5 次独立调用的值（ms）                | 中位数（ms） |
| ------------------------------- | ------------------------------------- | ------------ |
| 单次移动耗时中位数（30 样本内） | 0.032 / 0.031 / 0.031 / 0.033 / 0.032 | **0.032**    |
| 单次移动耗时最大值（30 样本内） | 0.662 / 0.622 / 0.590 / 0.616 / 0.592 | **0.616**    |

**达标**：中位数中位数 **0.032ms**，最大值中位数 **0.616ms**，均远低于 100ms
阈值——与 v0.3.0 `field-edit-latency` 的普通标量字段编辑（中位数 0.057ms）同一
量级，证明 10,000 行规模不改变主线程分发耗时的数量级。

### 执行时发现：假 Worker 必须如实模拟异步边界，否则会把 Worker 线程开销误算进主线程测量

第一版测试直接复用 v0.3.0 `field-edit-latency.perf.test.tsx` 的假 Worker 写法
（`postMessage` 内同步调用 `handleWorkerRequest`）。在 10,000 行规模下，这让
测得的"主线程分发耗时"跳到 80–130ms，在 `pnpm run check` 的全量并行执行下
数次越过 100ms 断言阈值。

排查定位到：`handleApplyPatch`（`apps/web/src/worker/protocol.ts`）把每次
patch 都包进 `HistoryStack.record()`，其 `before`/`after` 两次
`document.toText()` 在 10,000 规则规模下单次实测 **~7–13ms**（隔离测量，见下）：

```
toText() 单次（10,000 行文档）: 7–13ms
moveSeqItem 单次: 0.024–0.033ms（与 scale.bench.ts 记录的数字一致）
```

这本该是**真实 Worker 线程**上的开销——`Worker.postMessage()` 对调用方而言
天生异步，真实浏览器里这部分工作从不阻塞主线程——但假 Worker 的同步实现把它
错误地并入了"主线程"测量窗口。v0.3.0 的原始假 Worker 从未暴露这个问题，纯粹
是因为它测的标量字段设置太便宜，同步/异步两种假 Worker 实现测出来的数字都是
亚毫秒级、无法区分；只有当被测操作本身的 Worker 端耗时变得可观（大规模文档的
`toText()`）时，这个方法论层面的疏漏才会被放大到可观测、甚至可能导致断言失败
的程度。

**修复**：把假 Worker 的 `postMessage` 改成用 `queueMicrotask` 延迟处理请求
本身（不只是延迟发送响应），如实模拟真实 Worker 的异步边界。修复后数字回落到
上表记录的量级。这不是放宽阈值——是把测量对象改回 NFR-PERF-03 定义里本来就要
排除的"Worker 异步往返"之外；`HistoryStack.record()` 的 `toText()` 开销依然
真实存在，只是它发生在（真实场景中）从不阻塞主线程的 Worker 线程上，因此不
计入这项指标。

**遗留观察，供未来参考**：`HistoryStack.record()` 每次 `applyPatch` 调用两次
`document.toText()`，在 10,000 行规模下单次 ~7–13ms、两次约 15–25ms——这个
开销真实存在于 Worker 线程上，不影响本片的验收指标（编辑反馈的主线程耗时），
但会影响"编辑后 Undo/Redo 按钮状态更新、编辑器同步"这类**确实需要等 Worker
响应**的场景的观感延迟。这不是 v0.4.0 任何一片的验收范围（NFR-PERF-03/04 都
明确限定在主线程侧），如果未来版本需要优化大文档的整体编辑响应速度，
`document.toText()` 的重复调用（`HistoryStack.record()` 的 before/after 各一次，
且往往与调用方自己已经做过的一次 `toText()` 重复）是一个具体、有数据支撑的
优化起点。
