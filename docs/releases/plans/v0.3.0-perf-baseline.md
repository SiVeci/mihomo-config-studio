# v0.3.0 性能基线：常规字段编辑主线程耗时（NFR-PERF-03）

覆盖切片 #14。记录「表单字段的一次编辑」从 DOM 事件触发、经 `onChange` 回调链
（`SchemaForm`/`SchemaArrayForm` → `ModuleFormPage` → `ProjectPage` 的
`handleDocumentFieldChange`），到 Worker 的 `applyPatch` 请求被真正派发
（`WorkerClient#send` 内部同步的 `postMessage` 调用）为止，这段**纯主线程**耗时的
基线，退出条件是单次 < 100ms。

**口径限定**：只测主线程这一段，不测 Worker 往返（那是已经有独立断言的
`VALIDATION_DEBOUNCE_MS` 300ms 防抖窗口）——`fireEvent.change` 在
jsdom/React Testing Library 下是端到端同步的，`onChange` 回调链会在
`fireEvent.change` 本身返回之前、在同一个调用栈内跑完到第一个 `await`（也就是
`applyPatch` 请求已经同步派发出去的那一刻），所以直接测量 `fireEvent.change` 调用
本身的挂钟耗时即可，不需要另外等待 Worker 的异步响应。用真实挂钟
（`performance.now()`）而非注入的假时钟——假时钟与真实 CPU 耗时无关，回答不了
"到底花了多久"这个问题。数字来自本机开发环境，不是 CI 标准环境（与
`v0.2.0-perf-baseline.md` 口径一致）。

## 测试环境

| 项目     | 值                                                                                                                                                                                          |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| CPU      | Intel(R) Core(TM) i5-14600KF（20 逻辑核心）                                                                                                                                                 |
| 内存     | 31.8 GB                                                                                                                                                                                     |
| 操作系统 | Windows 10.0.26200（win32/x64）                                                                                                                                                             |
| Node.js  | v24.12.0                                                                                                                                                                                    |
| 测试文件 | `apps/web/src/form/field-edit-latency.perf.test.tsx`                                                                                                                                        |
| 测量方法 | 真实 `WorkerClient` + 真实 `handleWorkerRequest`（非 Worker 往返部分），对同一个真实 `general` 模块的 `mode` 字段连续做 30 次真实编辑，`performance.now()` 包住每次 `fireEvent.change` 调用 |
| 采样次数 | 5 次独立进程调用（`pnpm vitest run` 各跑一次），每次内含 30 个样本，记录该次的中位数与最大值                                                                                                |

## 结果

| 指标                                             | 5 次独立调用的值（ms）                | 中位数（ms） |
| ------------------------------------------------ | ------------------------------------- | ------------ |
| 单次编辑耗时中位数（每次调用 30 样本内取中位数） | 0.054 / 0.062 / 0.056 / 0.057 / 0.063 | **0.057**    |
| 单次编辑耗时最大值（每次调用 30 样本内取最大值） | 0.987 / 0.841 / 0.853 / 0.997 / 0.817 | **0.853**    |

**退出条件**：中位数中位数 **0.057ms**，最大值中位数 **0.853ms**，均远低于 100ms
阈值——中位数约 **1754 倍**余量，最坏情况样本也有约 **117 倍**余量。

## 复现方法

```bash
pnpm vitest run apps/web/src/form/field-edit-latency.perf.test.tsx --reporter=verbose
```

测试断言本身也直接把中位数与最大值都判在 100ms 阈值以内（`expect(...).toBeLessThan(100)`），
所以这不只是一份记录数字的旁路脚本——阈值回归是每次 `pnpm run check` 都会真实执行
的部分，不需要专门跑一次 bench 才能发现退化。

## 已知缺口 / 口径说明

- **只测了 `general` 模块的一个 `select` 字段（`mode`）**，未覆盖 `key-value`/
  `tags`/`SchemaArrayForm` 等更重的控件路径。给定当前 1754 倍量级的余量，以及
  `onChange` 回调链本身与具体控件类型无关（`FieldRow` 对所有控件统一走同一条
  `onChange(path, value)` 路径，参见 `packages/form-renderer/src/index.tsx`），
  没有为此专门再采样的必要；如果未来控件本身的 `onChange` 处理里长出真正昂贵的
  同步逻辑（例如同步跑一次复杂校验），才需要重新评估。
- **本机、非独占测试环境**：与 `v0.2.0-perf-baseline.md` 面临同样的限制（未特别
  隔离后台进程，未专门在最低支持版本 Node 20.11.0 上采样）。给定量级差距巨大
  （毫秒级阈值 vs. 亚毫秒级实测），环境噪音不足以影响"是否满足退出条件"这个结论。
- **只测「表单编辑」路径本身，不代表整条编辑体验的观感耗时**——用户真正感知的
  "编辑后多久看到反馈"还包含 React 的下一次渲染与（如果编辑触发了状态刷新）
  `client.value()`/`client.serialize()` 的 Worker 往返，这些都在 NFR-PERF-03 明确
  排除在外的范围（"不测 Worker 往返"），不是本文档要回答的问题。
