## 第一次推送：真实缺陷与修复

`core-config-test (stable)` 40/45，5 例失败，全部集中在 `proxies`/
`proxy-groups` 两个模块：

- `module-example:proxies:valid`/`:edge`/`:unknown-fields` 三例失败——
  根因是 `tools/core-test-runner/src/corpus.ts` 的合并策略：`proxies`
  模块的合并策略是 `array-element`（整体替换 `proxies:` 根），把
  `buildBaselineSkeleton` 硬编码的 `my-server-1`/`my-server-2`/`ss1`/`ss2`
  连同它们被 `PROXY` 选择组引用的事实一起冲掉，真实内核报
  `"PROXY: 'my-server-1' not found"`。**这是测试脚手架自身的 bug**，不是
  `schema-builtin` 内容的问题。修复：合并策略改为 `array-append`（追加而非
  替换），并把 `examples/valid.yaml` 里恰好与基线同名的 `ss1` 改名为
  `ss-example`，避免追加后与基线名字冲突。
- `module-example:proxies:edge` 失败——`wireguard` 分支的
  `examples/edge.yaml` 缺 `ip`/`ipv6`，真实内核报
  `"proxy 0: missing local address"`。这是**真实的 P0 schema 缺口**：
  `config.schema.json` 的 `wireguard` 定义只 `required` 了
  `type`/`public-key`/`private-key`，从未要求 `ip`/`ipv6` 二选一。修复：
  加 `"anyOf": [{"required":["ip"]},{"required":["ipv6"]}]`，`edge.yaml`
  补 `ip` 字段。
- `module-example:proxy-groups:edge`/`:unknown-fields` 两例失败——两个
  夹具都刻意省略了 `proxies`/`use`（`edge.yaml` 的原注释明文声称"select
  分支只需要 name 和 type"），真实内核报 "`use` or `proxies` missing"。
  这是**真实的 P0 schema 缺口**：
  `proxy-groups` 的共享分支从未要求 `proxies`/`use` 二选一。修复：加同样
  的 `anyOf` 约束，两个夹具补最小合法的 `proxies` 字段，注释改为准确表述。

以上两处 schema 内容变化改变了 `modules/proxies.json`/
`modules/proxy-groups.json` 的序列化字节，连带触发内置 Bundle 的 bootstrap
签名重签（`packages/schema-registry/src/builtin.ts`）——一次性密钥对签名后
立即丢弃，沿用既有流程；`version` 取 `0.9.1` 而非 `1.0.0`：现有测试夹具
（`ProjectPage.test.tsx`/`schema-resolution.test.ts` 等）已大量把字面量
`'1.0.0'` 当作"非内置"的任意已安装 Bundle 版本，若内置 Bundle 也用这个
版本号会与它们发生真实版本冲突（本轮已实测确认：`resolveProjectSchema`
把本该解析到已安装 signed Bundle 的用例解析成了 builtin）。

修复过程用真实 mihomo v1.19.29 二进制（在 WSL 里下载并核对
`sha256:60de76a35a6cbf7b4fa4a20f5c257c24345d1d635ab1aa3877022a1997ef413c`，
与 `download.ts` 里 `KERNEL_DIGESTS['linux-amd64']` 记录的值一致）逐个验证
过全部 45 个语料，确认修复后 45/45 符合预期，再推送。

对应提交：`8a9f579`。

## 对退出条件的影响

- v0.9.0 退出条件 1（内核矩阵全量，双轨）：**转为满足**，stable/beta 两轨
  均在真实 CI 上跑通，不再是"结构性证据"。
- v0.9.0 退出条件 2（E2E 三线全部通过并纳入 CI）：**Web 线部分满足**——
  `web.spec.ts`/`update.spec.ts` 全绿，但 `long-task.spec.ts` 的 NFR-PERF-05
  用例失败，整条 `Web E2E` job 因此报红。这不影响§13.5五条阻断项判定（见
  上表），但意味着 v1.0.0 计划进度表 #0 的"CI 全绿"要到 #2 落地并再次推送
  后才能真正兑现——**这是对 #0 原定"全绿"标准的一处如实记录的局部偏差**：
  #0 本身范围内能自解的两个真实缺陷（corpus.ts 合并策略、两个 P0 schema
  required 缺口）已修复且验证；`Web E2E` job 剩下的唯一红字是 #2 的既定
  工作范围，不在 #0 这一片重做，等 #2 提交后由那次推送的 CI 结果补齐"真正
  全绿"的证据，记录在本文件的后续更新里。
- v0.9.0 退出条件 5（五项性能指标达标且 CI 阻断）：PERF-02/03/04 的既有
  阻断阈值全部通过；PERF-05 的 CI 阻断（`long-task.spec.ts`）本轮真实观测
  为不达标——与基线表预判一致，#2 的工作范围。

  不变**——第 1–4 条本轮都拿到了真实 CI 绿证据（不再是结构性证据），第 5
  条（Android）按决策 I3 维持人工。
