# v0.6.0 先决项 2 —— 桌面浏览器更新链路复验证据

对应 [v0.6.0 执行计划](./v0.6.0.md) 切片 #0。版本文档先决项 2「v0.5.0 的更新链路在桌面浏览器上已跑通」在本仓库此前从未有过真实浏览器会话记录（`App.tsx` 的
`BundlePageRoute` 此前未接入任何 `updateSources`，安装路径只有组件测试覆盖）。本文件记录本片打通接线后，在真实桌面浏览器（本机 Claude Code Browser 面板，Chromium 内核）上实跑一次「检查更新 → 安装 → 回滚」全流程的证据。

## 环境

| 项目         | 值                                                                                                                                                 |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| 日期         | 2026-08-28                                                                                                                                         |
| 浏览器       | Claude Code Browser 面板（Chromium 内核）                                                                                                          |
| 服务方式     | Vite dev server（programmatic API，`node apps/web/scripts/dev-bundle-verify.mjs`），非 CLI `vite` 直启，原因见下「方法说明」                       |
| 地址         | `http://localhost:5480/#/bundle`                                                                                                                   |
| 更新源同源性 | 是——`test-bundle*` 放在 `apps/web/public/` 下，由同一个 dev server 以 `/test-bundle*` 路径提供，满足 `index.html` `connect-src 'self'` 的 CSP 约束 |

## 方法说明

`__BUNDLE_UPDATE_SOURCES__`/`__TRUST_ANCHOR_OVERRIDES__` 是 Vite `define`，在 **vite 配置求值时**读取 `process.env`，而 `.claude/launch.json` 的具名配置由宿主环境解析 `bash`/`cmd` 启动，路径与 PATH 在本机不稳定（`bash` 解析到 WSL、其 PATH 下找不到 `node`）。为避免依赖不确定的 shell，改用一个一次性脚本
`apps/web/scripts/dev-bundle-verify.mjs`：在 Node 进程内直接 `process.env.MCS_*_JSON = ...` 后调用 Vite 的 `createServer()`/`server.listen()` API 启动同一个 `apps/web` 项目——配置读取路径与真实 `vite`/`vite build` 完全一致，只是启动方式从 CLI 换成等价的 JS API，不影响验证结论的有效性。该脚本与 `.claude/launch.json` 里的 `mcs-web-bundle-verify` 临时条目、`apps/web/public/test-bundle*` 两个签名测试 Bundle，均在本次复验完成后删除，不进入提交。

测试 Bundle 由 `tools/schema-cli` 的真实 `packDirectory`/`signManifest`（`canonicalManifestJson` 同一份签名口径）生成——通过 vitest 的模块图运行（本仓库工作区包互相以 `.js` 扩展名引用 `.ts` 源码，ADR-007，只有 Vite/Vitest 的解析器认得这种映射，纯 `node` 直接执行会在 `ERR_MODULE_NOT_FOUND` 上失败），而不是手写等价逻辑——这样验证的是生产签名/打包代码本身，而非一份可能与其行为不同的临时实现。两个 Bundle 用同一个临时生成、从未落盘保存的 Ed25519 密钥对签名；该密钥的公钥通过 `MCS_TRUST_ANCHOR_OVERRIDES_JSON` 注入为本次验证专用的信任锚点覆盖，与生产/内置引导密钥无关。

## 步骤与观察

### 1. 初始状态（清空 IndexedDB 后刷新）

- 页面文案：「当前 Bundle」显示 Bundle ID `builtin`、版本 `0.5.0`、通道 `stable`、Mihomo 兼容范围 `1.19.29 – 1.19.29`（内置 Bundle，未做任何安装前的真实状态)。
- 「检查更新」区块渲染「检查并安装」按钮——证明 `updateSources.stable` 已被 `BundlePage` 识别为已配置（先决项 2 要修的接线点：此前 `App.tsx` 未传 `updateSources`，这里会显示「未配置」文案而不是按钮）。
- 「回滚」区块文案：「没有可回滚的历史版本」。

### 2. 第一次安装（0.5.0 → 0.6.0，更新源指向 `apps/web/public/test-bundle/manifest.json`）

- 点击「检查并安装」。
- 「当前 Bundle」版本变为 `0.6.0`。
- 「检查更新」区块出现 `status` 文案：「安装成功，已切换到新版本」。
- 「回滚」区块仍显示「没有可回滚的历史版本」——**符合预期**：这是该 channel 的第一次真实安装，`previous` 槽位此前从未被写入过，不是 bug。

### 3. 第二次安装（0.6.0 → 0.6.1，更新源改指向 `apps/web/public/test-bundle-v2/manifest.json`，重启 dev server 使新 env 生效，浏览器 IndexedDB 未清空）

- 刷新页面：「当前 Bundle」仍显示 `0.6.0`（确认 IndexedDB 持久化、跨进程重启有效）。
- 点击「检查并安装」。
- 「当前 Bundle」版本变为 `0.6.1`。
- `status` 文案：「安装成功，已切换到新版本」。
- **「没有可回滚的历史版本」文案消失**，「回滚到上一版本」按钮可用——两个槽位（active = 0.6.1，previous = 0.6.0）同时存在，正是版本文档先决项 2 要求的场景。

### 4. 回滚

- 点击「回滚到上一版本」。
- 「当前 Bundle」版本变回 `0.6.0`（active 复位）。
- `status` 文案：「已回滚到上一版本」。

### 5. 控制台

`read_console_messages` 全程无应用级错误；仅有本次临时 `createServer()` 启动方式自身重启时产生的 Vite HMR WebSocket 重连噪音（`WebSocket connection to 'ws://localhost:5480/' failed`），与被验证的更新/回滚逻辑无关，且不会出现在 `vite`/`vite preview` 的正常单次启动场景下。

## 结论

先决项 2「v0.5.0 的更新链路在桌面浏览器上已跑通」——**本片起满足**：`App.tsx` 已接入
`resolveUpdateSources()`；真实浏览器会话验证了检查、首次安装（无回滚槽位）、二次安装
（两槽位出现）、回滚（active 复位）四个状态迁移，全部通过 UI 文案而非直接读 IndexedDB
确认。跨源更新场景（真实 GitHub Releases 源）不在本片范围，留给 #12（决策 Q2：Beta 阶段默认不配远端源）。
