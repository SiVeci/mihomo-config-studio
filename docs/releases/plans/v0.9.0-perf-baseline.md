## #11：NFR-PERF-05 真实浏览器 long-task 测量

**目标**：v0.2.0 决策 D3 把"引擎只运行在 Worker 里"这件事的 timing 证据
（区别于 `client.test.ts`「main-thread module boundary」的静态扫描结构性
证据）留到本版本。用真实浏览器的 Long Tasks API（jsdom 没有主线程、也没有
`PerformanceObserver` 的 `longtask` 实现）测量三个真实动作——导入 1 MB
语料、（debounce 触发的）全量校验、`DiffPanel` 重新计算差异——期间主线程
long task 数是否为零。

**测试文件**：`e2e/long-task.spec.ts`（Playwright，ADR-033 的 E2E 层）。

**结果：Partial，如实记录（不宣告 Done）。**

### 第一个真实发现：`SchemaArrayForm` 完全没有虚拟化

首次真实运行（真实 Long Tasks API，真实浏览器）测到一个 **1.5 秒**的主线程
long task。定位：`packages/form-renderer/src/index.tsx` 的 `SchemaArrayForm`
（`proxies`/`proxy-groups`/`proxy-providers`/`rule-providers` 四个数组型模块
共用的渲染器）对每个数组条目用一个普通 `.map()`——不做任何虚拟化。本文件用的
1 MB 语料（`generateLargeCorpus()`）里有 **3,182 个 proxies**——导入后默认
显示的"表单"标签页会把这 3,182 个条目一次性同步渲染成真实 DOM 节点。

**这是一个此前从未被验证过的真实缺口**：NFR-PERF-04（"长列表必须虚拟化"）
在 v0.4.0 #7/#14/#15 只验证过**规则列表**（`RuleListPage`，`packages/ui`
的 `computeVirtualWindow`，定高虚拟化），代理列表这条长列表在真实规模下
从未被测过。

### 已修复：给 `SchemaArrayForm` 加变高虚拟化

`packages/ui/src/virtual-list.ts` 新增 `computeVariableVirtualWindow`——
`computeVirtualWindow` 的变高版本（ADR-022 自己在"什么情况下应该
supersede"一节已经预判了这个场景："如果规则列表需要变高行...需要扩展
`computeVirtualWindow` 或换用支持变高的方案"）。代理表单条目是完整子表单
（不同 `type` 字段数不同、`basic`/`advanced` 模式也会变），不是规则列表那种
定高行，不能直接套用定高算法。`SchemaArrayForm` 照抄 `RuleListPage` 的
`ResizeObserver` + `scrollTop` 接线方式，加一层"渲染后用 `useLayoutEffect`
量真实高度、修正估算值"的纠偏循环。容器高度需要 CSS 给一个明确的
固定值（`apps/web/src/form/ModuleFormPage.css` 的 `[data-array-form]`
规则）——这一步在实现时踩过一次真实的坑：如果容器没有固定高度，
`ResizeObserver` 量到的是"内容当前有多高"而不是"视口有多高"，这是一个
自我指涉的目标（渲染多少条目决定了测出来的高度，测出来的高度又反过来决定
渲染多少条目），会让两者互相追逐而不收敛，而不是一次性稳定下来。

**验证**：`packages/ui/src/virtual-list.test.ts` 新增 22 例覆盖
`computeVariableVirtualWindow`（含"等同于定高版本""3,182 条真实规模窗口
远小于总数"等场景）；`apps/web/src/form/proxies-array-form-scale.perf.test.tsx`
用真实 `@mcs/schema-registry` 的 `proxies` 模块定义 + 真实
`generateLargeCorpus()` 语料渲染 `SchemaArrayForm`，断言 DOM 条目数
< 100（与 `rule-list-scale.perf.test.tsx` 同款断言形状）——**通过**，
3,182 个真实代理条目只渲染出个位数到十几个 DOM 节点。手动真实浏览器复现
（简化语料，未混入本片下述的第二个发现）也确认了虚拟化生效、渲染速度快。

### 第二个真实发现：修复未完全消除 long task，且怀疑另有环境噪声

把这个虚拟化修复接上真实 E2E 后重跑，**同一个 assertion 仍然失败**：
主线程仍然测到一个 long task，这次是 **2.044 秒**（比修复前的 1.5 秒还长，
但同一数量级、同一性质——不是回归到更差，是同一个待解决问题的另一次采样）。

**新的怀疑对象，未修复，如实记录**：`buildArrayFormPlan(module, value, ...)`
本身对**全部** 3,182 项做规划（生成 `PlannedField[]`），本片只把"规划结果
切片渲染"这一步虚拟化了，规划计算本身完全没有按窗口裁剪。手动测量：单次
`buildArrayFormPlan` 调用（真实 3,182 项）耗时 **130–140ms**；如果组件在
高度纠偏循环里重新渲染好几次（每次都要重新调用一次这个未裁剪的规划
函数），累加起来足以解释一个上 1–2 秒的 long task。这是下一步最值得先查的
线索，但本片未验证、未修复。

**另一个独立、尚未解释的现象**：这条 E2E 测试整体运行耗时在本机变得不稳定
（同一语料、同一台机器，从约 40 秒到 100+ 秒不等），而且**这个不稳定在完全
未改动的原始代码上同样复现**（用 `git stash` 隔离验证过）——说明这至少
部分是环境层面的噪声，不是这个虚拟化修复引入的回归。因为这条独立噪声的
存在，`e2e/long-task.spec.ts` 的等待超时相应放宽（120s/150s），如实记在
测试文件自己的注释里，而不是假装问题不存在。

### 判定

| 项目                             | 结论                                                                          |
| -------------------------------- | ----------------------------------------------------------------------------- |
| `SchemaArrayForm` 缺虚拟化的发现 | **真实**，已确认（1.5s long task，3,182 个未虚拟化 DOM 节点）                 |
| 虚拟化修复（DOM 节点数）         | **已修复**，已验证（jsdom 3,182→<100 节点；真实浏览器手动复现）               |
| Long task 完全消除               | **未达成**——修复后仍测到 ~2s long task，根因怀疑但未验证                      |
| NFR-PERF-05（本片目标）          | **Partial**——真实 timing 证据已建立，且已修好一个真实发现，但断言本身仍不通过 |
| NFR-PERF-04（代理列表虚拟化侧）  | **Partial**——渲染虚拟化已验证，规划计算虚拟化未做                             |

**因此本片（v0.9.0 #11）如实记 Partial，不宣告 Done**——过程中发现并修复了
一个真实、此前从未被验证过的核心需求缺口（NFR-PERF-04 对代理列表的适用性），
这是真实的、可审查的进展；但本片最初的验收目标（这条 E2E 断言本身通过）
未达成，且还有一条独立、未解释的环境噪声一并如实记录。

### 接下来谁来做什么

1. 验证"`buildArrayFormPlan` 未裁剪"这个怀疑：给 `buildArrayFormPlan` 的
   调用现场加计时，或者直接改造成只对当前虚拟化窗口内的条目做规划——需要
   处理好索引映射（`FieldRow` 的编辑回调要指向条目在**完整数组**里的真实
   路径，例如 `/proxies/1500`，不能是切片后的局部下标）。
2. 如果修复后 long task 消失，`e2e/long-task.spec.ts` 的断言应该自然转绿，
   NFR-PERF-04/05 都可以从 Partial 转 Done。
3. 独立追查那条"整体运行耗时不稳定，原始代码同样复现"的环境噪声——不属于
   本片范围，但值得记一笔留给以后：可能是本机长会话下的资源争用（这次
   会话已经跑了大量并发 build/test/browser 进程），也可能是这个具体测试
   场景（大语料 + 真实 Worker + 真实浏览器）本身有某个尚未理解的成本来源。
