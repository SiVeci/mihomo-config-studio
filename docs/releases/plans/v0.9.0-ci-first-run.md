## 为什么这件事本身就是证据

在此之前，`origin/main` 上只有一条 `ee97ccc Initial commit`，本地领先 **169 个
提交**，**CI 从未在任何真实内容上运行过一次**。因此在本片之前，本仓库任何
"某个 CI job 通过"的说法都只是本机说法：

- v0.3.0 退出条件 5、v0.4.0 退出条件 7、追踪表 §13.3「内置模板内核测试」三处
  记的都是 **Done（结构性）**，理由都是"真实下载并执行内核二进制这一步本身尚未
  被本人直接观测到成功"。
- v0.6.0 退出条件 #2 记着"产物级检查现已接入 `release.yml`，尚未经真实 CI 运行验证"。

本片把这些口径全部改成真实证据——或者暴露它们其实不成立。

## 逐个问题

### 问题一（run 1）：`pnpm/action-setup@v4` 的版本冲突，五个 job 全部 13 秒内死在同一步

```
Error: Multiple versions of pnpm specified:
  - version 10 in the GitHub Action config with the key "version"
  - version pnpm@10.34.5 in the package.json with the key "packageManager"
```

动作输入与 `packageManager` 字段同时指定版本时，`pnpm/action-setup@v4` 直接拒绝
运行。去掉三个 workflow 里全部九处 `with: version: 10`，让 `packageManager` 成为
唯一来源——顺带比原来更严格（`packageManager` 钉的是精确的 `10.34.5`，`version: 10`
只是大版本范围）。

**这个错误在本机无论如何都跑不出来**，因为本机根本不经过 `pnpm/action-setup`。

### 问题二（run 2）：Node 20 上 38 个测试文件静默不执行，而且看起来像通过了

```
Test Files  81 passed (119)
     Tests  1509 passed (1509)
    Errors  38 errors
 Duration   26.76s (… environment 27ms …)
```

38 条 `TypeError: webidl.util.markAsUncloneable is not a function`——`jsdom@30.0.1`
经 `undici@8.10.0` 调用了一个 Node 22 才有的 API，jsdom 整个装不起来，**全部 38 个
DOM 测试文件一个都没跑**。

**最危险的是它的失败形态**：vitest 把这些记成 "unhandled errors" 而不是失败用例，
摘要行写的是 `81 passed` 和 `1509 passed`，**没有一个红色用例**。拦下这次假绿的
是覆盖率闸门（**64.2% < 85%**）——不是任何断言。

> 这给「85% 阈值不得放宽」补了一条计划里没写的理由：它同时是**捕获静默不执行的
> 最后一道防线**。

### 问题三（run 2，同批）：编译后的 `tools/*` CLI 在 Node 20 上无法启动

```
TypeError [ERR_UNKNOWN_FILE_EXTENSION]: Unknown file extension ".ts"
  for …/packages/templates/src/index.ts
```

`tools/core-test-runner/dist/index.js` 里 `import … from '@mcs/templates'` 的模块
说明符被 `tsc` 原样保留，Node 顺着 workspace 链接解析到 [ADR-007](../../adr/ADR-007-source-only-workspace-packages.md)
约定的 `exports: "./src/index.ts"`。本机之所以从没发现，是因为本机是 Node 24，
默认开启类型剥离。

问题二与问题三合并由 [ADR-030](../../adr/ADR-030-minimum-node-baseline.md) 处理：
最低 Node 抬到 **22.18**（`engines`、三个 workflow 的十处 `node-version`、
`README.md`、`CONTRIBUTING.md`）。**没有只改 CI 而留着假的 `engines`。**

### 问题四（run 3）：`corpus.test.ts` 10 秒超时

`packages/validator/src/bench/corpus.test.ts:37` `Test timed out in 10000ms`。
10s 这个余量在本机够，在 2 核共享 runner + v8 插桩下不够。v0.6.0 计划风险 R2
已经预测过（"若 CI 也复现，应把它和 R2 一起处理"），这就是那次复现。

放宽的是**正确性测试上的墙钟守卫**（两条断言是"无语法问题"与"无阻断问题"，一字
未改），不是性能阈值。真正的慢点由 #10/#11 用真实阈值去测。

### 问题五（run 4，两次确定性复现）：一个真实的产品竞态

```
apps/web/src/project/ProjectPage.test.tsx:781
「Redo restores the edited text byte-exact after an undo」
AssertionError: expected true to be false
```

- 本机隔离跑 **8/8 通过**
- 本机 Node 22 隔离跑 **8/8 通过**
- 本机全量套件限制 2 线程 + coverage **通过**
- CI 上 **2/2 失败**（含一次 `gh run rerun --failed`）

不是偶发，是环境相关的确定性差异。用协议层单测**确定性复现**（无 React、无计时器）：

```
parse → applyPatch → undo → parse(撤销之前的旧文本) → redo
⇒ redo 返回 canUndo: false
```

**机制**：`YamlEditor` 的防抖 effect 在 `text` 变化 300ms 后重新 `parse`，而
`ProjectPage` 把每个 undo/redo 响应的 text 直接喂回那个 prop。计时器触发与 React
提交新 prop 之间存在缝隙——effect 的 cleanup 还没来得及 `clearTimeout`，计时器就
带着**撤销之前的旧文本**发出了 parse。`handleParse` 的回声判定只比对"当前文档
文本"，这条迟到的请求于是被判成"一份全新文档"，把 `historyStack` 整个清空。

这正是 `handleParse` 自己的注释里警告的那个灾难（v0.3.0 #15 在真实浏览器里手工
抓到过一次），只是这次是从**相反方向**撞进来的：那次担心判定太松，这次是判定太紧。

**修复**：回声判定从"等于当前文本"放宽为"当前文本，或历史栈认识的任一状态"
（新增 `HistoryStack#knowsText`）。凡是能被 undo/redo 走到的状态，按定义就还是
"这份文档"。

**`ProjectPage.test.tsx` 一字未改**——它正确地抓到了一个真实缺陷，改它才是错的。

## `perf-baseline` 的真实 CI 数字（#10 的输入）

以下是 GitHub `ubuntu-latest` 共享 runner 上的实测值，与本机数字并列。**本片只
记录，不据此调整任何阈值**——定阈值是 #10 与 ADR-034 的事。

### `import.bench.ts`（1 MB 语料，NFR-PERF-02，阈值 2000ms）

| 项                                     | CI mean        | CI min   | CI max   | 本机中位数（v0.2.0 基线） |
| -------------------------------------- | -------------- | -------- | -------- | ------------------------- |
| `parse`                                | 383.53ms       | 360.57   | 425.37   | —                         |
| `first validation pass (pre-parsed)`   | 5 216.86ms     | 5 071.40 | 5 392.78 | —                         |
| **`parse + first validation (total)`** | **4 086.22ms** | 3 922.44 | 4 605.19 | **580.57ms**              |

> **必须显眼记录的发现：NFR-PERF-02 在 CI 硬件上不达标。** 退出条件写的是
> 「1 MB YAML 导入、解析和首轮校验 **< 2 秒**」，CI 实测 **4 086ms，超标约 2 倍**；
> 本机同一基准是 580ms，有 3.4 倍余量。两者相差约 7 倍。
>
> 这直接推翻了计划 #10「余量极大，阻断的真实风险不在'指标不达标'而在'CI 噪声造成
> 假失败'」这句判断——**在 CI 硬件上它是真的不达标**，不是噪声。
>
> #10 必须先回答一个此前没被问过的问题：**NFR-PERF-02 的 2 秒是对着什么硬件说
> 的？** 是用户的机器，还是 CI runner？PRD §11.1 没有指定。在回答之前不能把这条
> 变成阻断闸门，也不能因为"CI 慢"就把阈值放宽——两种做法都是在回避问题。
> 这条留给 #10 与 ADR-034，**本片不做决定**。

  说明这件事比计划预想的更需要先想清楚。

  基线声明与事实不符（抬版本号 + 新 ADR），一个是墙钟守卫（断言未动），一个是
