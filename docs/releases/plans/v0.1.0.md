### #1 `config-model` 实体与稳定 ID

**目标**：从 YAML 文档提取带内部稳定 ID 的领域实体，ID 与序列化名解耦。

**覆盖**：FR-REL-01。

**涉及文件**

- 新建：`packages/config-model/package.json`、`tsconfig.json`、`src/index.ts`、
  `src/entity.ts`、`src/entity.test.ts`
- 修改：`tsconfig.build.json`（加 `./packages/config-model` 引用）

**实现要点**

- `Entity = { id, kind, serializedName, sourcePath }`，`kind` 取
  `proxy | proxy-provider | proxy-group | rule-provider | rule | sub-rule`。
- 提取点：`proxies[].name`、`proxy-groups[].name`、`proxy-providers.<key>`、
  `rule-providers.<key>`、`rules[]`、`sub-rules.<key>[]`。
- **ID 生成策略是本片的核心决策**：`id` 必须在 `serializedName` 改变后保持不变，
  且不得进入导出的 YAML。建议 `kind` + 会话内单调计数器（`proxy-group:3`），
  由 Registry 持有 `id → Entity` 映射；不要用名字哈希——那样改名就换 ID。
  `sourcePath` 是可变的定位信息（序列下标会因插入/删除移动），不能参与 ID。
- 内置目标作为预置实体（`kind: 'builtin'`）纳入，否则 #3 会把它们误判为断裂引用。
  v1.19.29 `config.go#parseProxies` 逐字确认的六个：`DIRECT`、`REJECT`、
  `REJECT-DROP`、`COMPATIBLE`、`PASS`、**`PASS-RULE`**。`GLOBAL`（隐式全局选择器组）
  实现时已再次核对同一函数源码：`GLOBAL` **确实**进 `proxies` 映射，但只在
  `!hasGlobal` 时才由 upstream 自动创建——若用户在 `proxy-groups[]` 里自定义了一个
  名为 `GLOBAL` 的组，upstream 用用户的组代替自动创建，不会冲突报错（与前六个不同，
  那六个是无条件保留字，重名直接报错）。因此实现里 `GLOBAL` 是**条件**内置实体：
  仅当提取结果里没有 `serializedName === 'GLOBAL'` 的 `proxy-group` 时才补一个
  `kind: 'builtin'` 的 `GLOBAL`。
- 仅依赖 `@mcs/yaml-engine` 的只读 API（`getIn`、`leafPaths`），不触发结构化改写。


### #2 规则字符串子片段定位器

**目标**：把一条规则字符串解析成带字节偏移的字段序列，精确定位其中的引用片段。

**覆盖**：FR-REL-02 的风险核心（版本文档「已知技术难点」）。

**涉及文件**

- 新建：`packages/config-model/src/rule-line.ts`、`src/rule-line.test.ts`
- 修改：`packages/config-model/src/index.ts`（导出）

**上游口径（2026-08-10 已核对，取代原保守假设）**

依据 `MetaCubeX/mihomo` tag **v1.19.29** 的 `rules/common/base.go#ParseRulePayload`
（逐字源码，非记忆）：

```go
item := trimArr(strings.Split(ruleRaw, ","))
tp = strings.ToUpper(item[0])
if len(item) > 1 {
	switch tp {
	case "MATCH":
		target = item[1]
	case "NOT", "OR", "AND", "SUB-RULE", "DOMAIN-REGEX", "PROCESS-NAME-REGEX", "PROCESS-PATH-REGEX":
		if needTarget {
			l := len(item)
			target = item[l-1]
			item = item[:l-1]
		}
		payload = strings.Join(item[1:], ",")
	default:
		payload = item[1]
		if len(item) > 2 {
			if needTarget {
				target = item[2]
				if len(item) > 3 {
					params = item[3:]
				}
			} else {
				params = item[2:]
			}
		}
	}
}
```

结论与原假设的差异：**逻辑规则与 `DOMAIN-REGEX` 完全可以可靠定位**——它们走
「target 取最后一段」分支，且**没有 params**，所以含逗号的 payload 不造成歧义。
`unresolved` 回退不需要了，v0.4.0 也无需补课。本片按上游算法 1:1 实现。

**实现要点**

- 输出 `{ type, payload, target, params[] }`，每段带 `[start, end)` 偏移，
  使调用方能只替换 target 片段而保留原字符串其余字节。
- 三分支照抄上游，**不要自创口径**：
  - `MATCH` → `target = item[1]`，无 payload 无 params。
  - `NOT|OR|AND|SUB-RULE|DOMAIN-REGEX|PROCESS-NAME-REGEX|PROCESS-PATH-REGEX`
    → target 取**最后一段**，payload 是中间各段用 `,` 重新拼接。
  - 其余（default）→ `payload = item[1]`、`target = item[2]`、`params = item[3:]`。
    target 是**固定的第 3 段**，不是最后一段，**不能用 `split(',').pop()`**。
- `trimArr` 对每段去首尾空白，因此 `DOMAIN , example.com , PROXY` 合法。
  偏移必须落在**去空白后的实体片段**上，否则改名会把空格吃掉。
- `strings.ToUpper(item[0])`：规则类型**大小写不敏感**，`domain-suffix` 等价于
  `DOMAIN-SUFFIX`；分支判定前先归一化。
- `RULE-SET,<name>,<target>` 走 default 分支：**两个位置都是引用**——`payload`
  指向 rule-provider，`target` 指向 proxy-group / 内置目标。
- `SUB-RULE` 走特殊分支，其 target 指向**子规则名**而非代理组
  （`config.go` 对 `tp == "SUB-RULE"` 单独查 `subRules` 映射），
  引用类型必须区分开，否则 #4 的影响分析会找错对象。
- default 分支的 payload **不能含逗号**（只取 `item[1]`）——上游同样会静默错解。
  本片按上游行为实现，不做「更聪明」的补救；若解析结果与用户意图不符，
  由 #4 的校验产出 issue，而不是在解析层猜。
- 纯字符串处理，无 I/O、无正则回溯风险（NFR-SEC-05）。

**验收命令**

```bash
pnpm run check && pnpm run format:check
```

**验收要点**

- `comprehensive.yaml` 的 10 条规则逐条断言 target 偏移。
- `IP-CIDR,198.18.0.0/16,REJECT,no-resolve` 的 target 是 `REJECT` 不是 `no-resolve`
  （default 分支取第 3 段）。
- `RULE-SET,cn-domain,DIRECT` 产出两个引用片段，且两者引用类型不同。
- `DOMAIN-REGEX,^ad[0-9]*\.example\.com$,REJECT` target 取最后一段。
- `AND,((DOMAIN,a),(DOMAIN,b)),PROXY` → target `PROXY`，
  payload 重新拼接后等于 `((DOMAIN,a),(DOMAIN,b))`（**逗号不丢**）。
- `DOMAIN-REGEX,a{1,2},REJECT` → target `REJECT`，payload `a{1,2}`。
- `domain-suffix,local,DIRECT`（小写）与大写版本解析结果一致。
- `DOMAIN , example.com , PROXY` → target 偏移不含两侧空格；用该偏移改名后
  原有空格排布保持不变。

**完成后更新的文档行**：无（并入 #5 一次性更新）。

### #3 `graph` 引用索引与级联改名

**目标**：建立引用索引并实现无损级联改名，改动行集合可被差异断言。

**覆盖**：FR-REL-02。

**实现要点**

- `Reference = { fromId, toId, path, referenceType }`，`referenceType` 至少区分

  `setScalarIn()`，后者先用 #2 的偏移拼出新字符串再整体写回。三者都能在 CST 模式下
  保住引号风格与 flow 样式。

- 索引建立后文档发生结构性改动（`appendIn` / `deleteIn` / `moveSeqItem`）会使
  `sourcePath` 失效，索引需提供显式 `rebuild()`，不要试图增量维护。

### #8 Bundle 哈希与签名校验

**目标**：完整实现更新前校验，三类否定用例全部拒绝。

**覆盖**：FR-UPD-03、NFR-SEC-04。

**依赖**：#6（后端策略）、#7（manifest 类型）。

**涉及文件**

- 新建：`packages/schema-registry/src/verify.ts`、`src/verify.test.ts`
- 新建：`packages/schema-registry/src/testing/keys.ts`（测试用密钥对与向量）

**实现要点**

- 校验顺序固定且短路：`formatVersion` → `requiresApp` → 逐文件 SHA-256 → manifest
  签名。先做便宜检查，签名放最后。
- 签名覆盖 manifest 本身（ADR-010 §1），因此逐文件哈希写在 manifest 里、签名护住
  manifest，构成完整性链。序列化 manifest 用**确定性 JSON**（键排序、无多余空白），
  否则签发端与验证端字节不同会导致假阴性。这是本片最容易踩的坑。
- 信任锚点是公钥**数组** `[current, next]`（ADR-010 §3），任一验过即通过。
  公钥以常量内置在包里，不从 Bundle 读取。
- 验签走 #6 定的 `Ed25519Verifier` 端口；本版本只提供 SubtleCrypto 实现，
  端口留给 v0.5.0 接纯 JS 回退。
- 失败原因用错误码枚举（`BUNDLE_HASH_MISMATCH` / `BUNDLE_SIGNATURE_INVALID` /
  `BUNDLE_FORMAT_UNSUPPORTED` / `BUNDLE_APP_TOO_OLD`），消息不含哈希全串、
  不含文件内容（NFR-SEC-03）。

**验收命令**

```bash
pnpm run check && pnpm run format:check
```

**验收要点**（版本文档要求的三类否定用例，缺一不可）

1. 篡改 Bundle 内某个文件一个字节 → `BUNDLE_HASH_MISMATCH`。
2. 用另一把私钥重新签名 → `BUNDLE_SIGNATURE_INVALID`。
3. `formatVersion` 超出支持范围 / `requiresApp` 高于当前版本 → 对应错误码。

外加正向用例：内置 Bundle 与正确签名的测试 Bundle 通过全部四步。

**完成后更新的文档行**：无（并入 #10）。

### 本版本的口径调整（2026-08-10 决策，非静默变更）

版本文档退出条件写的是「Android **真机**链路在**两个版本**上跑通」。本机无可用真机，
现有系统镜像最低为 android-29，经决策改为：

- **本版本以模拟器 `Medium_Phone_API_29`（Android 10）+ `V14_API36_Large` 为证据**；
- **真机验证整体推迟到 v0.6.0（M5 Android 集成）**；
- 追踪表 M0-5 因此记 **Partial** 而非 Done，缺口列写明「无真机证据」；
- NFR-PERF-01 的基线数字标注「模拟器口径」，v0.6.0 必须用真机复测。

这是对版本文档退出条件的**显式降级**，不是解释。#14 收口时该条不得勾为完全满足，
必须在版本文档退出条件处注明本调整与承接版本。
