# v0.6.0 性能基线：产品壳冷启动与首次可交互（NFR-PERF-01 复测）

覆盖切片 #11。ADR-014 的 412ms/586ms 数字来自 v0.1.0 的空白 spike 页
（`apps/android`，一次性技术验证壳，`applicationId` 为
`studio.mihomoconfig.m0spike`），本片测的是 v0.6.0 #3 起替换的产品 Android 壳
（`applicationId` 为 `studio.mihomoconfig.app`）——真实 App 图标、真实 WebView
内容（完整 React 应用，非探测页）。

## 口径限定（同 ADR-014，G1）

全部数据来自 Android 模拟器（AVD），x86_64，宿主机为本机开发机（Windows，
`i5-14600KF`），不代表真机性能，也不能跨机器/跨环境直接比较。两台设备：
`Medium_Phone_API_35`（中端代表）、`V14_API36_Large`。API 29 按计划风险 R1
预期会先撞 ADR-027 的启动能力门，不参与冷启动数字采样，单独一节记录确认结果。

## 测量方法

- **进程级（TotalTime）**：`adb shell am start -W -n <appId>/.MainActivity`，
  每次测量前先 `adb shell am force-stop <appId>` 确保是真冷启动（而非复用已
  驻留进程的热启动）。这个数字只到 Activity 可见为止，WebView 内的 React 树
  是否已挂载不影响它。
- **页面级（MCS_FIRST_INTERACTIVE_MS）**：`apps/web/src/App.tsx` 的
  `useReportFirstInteractive()`——`useEffect`（而非 `useLayoutEffect`，为了
  确保在浏览器已提交并绘制首屏之后触发）记一个
  `performance.mark('mcs-first-interactive')` 并 `console.warn` 一行
  `MCS_FIRST_INTERACTIVE_MS=<ms>`，经 `adb logcat` 读回。这是"用户真正能点
  东西"的时间点，`TotalTime` 答不了这个问题——两个数字量的不是一件事，两个
  都要记，只报前者会得到一个好看但无意义的数字。
- 每台设备每个指标采样 7 次（高于计划要求的 5 次下限），取中位数，方法沿用
  ADR-014。

## 结果

| 设备                  | Android / API | TotalTime 中位数（7 次） | MCS_FIRST_INTERACTIVE_MS 中位数（7 次） | NFR-PERF-01 阈值 | 结果     |
| --------------------- | ------------- | ------------------------ | --------------------------------------- | ---------------- | -------- |
| `Medium_Phone_API_35` | 15 / 35       | 710ms                    | 396ms                                   | < 2500ms         | **通过** |
| `V14_API36_Large`     | 16 / 36       | 796ms                    | 422ms                                   | < 2500ms         | **通过** |

原始 7 次采样值（ms）：

- `Medium_Phone_API_35` TotalTime：707、707、710、713、646、727、828
- `Medium_Phone_API_35` MCS_FIRST_INTERACTIVE_MS：455、387、339、396、414、371、579
- `V14_API36_Large` TotalTime：962、729、928、719、618、905、796
- `V14_API36_Large` MCS_FIRST_INTERACTIVE_MS：580、414、491、410、239、549、422

两台设备的两个指标中位数均远低于 2500ms 阈值——最差情况是 `V14_API36_Large`
的 TotalTime 796ms，距阈值仍有约 68% 余量。均达标，不触发"看构建产物体积是否
阻塞首屏"的排查分支（该分支只在不达标时才需要）。

## 与 ADR-014 spike 数字的对比：变慢符合预期

spike 页不加载任何真实模块、不初始化 Config Worker、不做任何 Schema/能力探测；
产品壳要挂载完整 React 路由树、启动真实 Worker、跑一次 Ed25519 能力探测
（ADR-028 的 `resolveEd25519Verifier()`）等真实初始化路径，TotalTime 从
412/586ms 涨到 710/796ms 符合预期，且两个指标都仍有充分余量。

## API 29：确认命中 ADR-027 能力门，不参与冷启动采样

计划风险 R1 预期 API 29 会先在能力探测阶段命中 ADR-027 的"浏览器版本过旧"门
（`String.prototype.replaceAll`/`Array.prototype.at`/`Object.hasOwn` 缺失），
而非进入可测量"首次可交互"的正常路径。本片额外做了一次自主补充核实（非计划
要求的第三台设备，计划本身只要求 API 35 + API 36 两组数字）：在
`Medium_Phone_API_29` 上安装产品壳并 `adb shell am start -W` 冷启动，结果为
`TotalTime: 919ms`（Activity 可见，能力门页面本身也是一次真实 React 挂载，
所以这个数字仍然存在），随后用 `adb exec-out screencap` 截图确认页面内容——
渲染的是中英双语的「浏览器版本过旧 / Browser Version Too Old」文案，列出缺失
的三个能力，而非应用界面，与预期一致。这次挂载**没有**输出
`MCS_FIRST_INTERACTIVE_MS`：能力门分支在探测失败时提前 `return`，不会执行到
`useReportFirstInteractive()`——因此 API 29 没有独立的"首次可交互"数字，这是
设计使然（该设备本就不支持运行本应用的正常路径），不是遗漏。

## 复现方法

```bash
adb shell am force-stop studio.mihomoconfig.app
adb shell am start -W -n studio.mihomoconfig.app/.MainActivity
adb logcat -d | grep MCS_FIRST_INTERACTIVE_MS
```

## 已知缺口 / 口径说明

- 同 ADR-014：模拟器口径，真机基线不在本片范围。
- 未测 API 29 之外更旧的镜像——本机可用最旧镜像即 API 29，ADR-014 已把它定为
  已验证下限，本片不重复论证；本片对 API 29 的补充测量只用于确认能力门按预期
  拦截，不代表对该设备做冷启动达标性判定（该设备设计上就不应进入应用主流程）。
