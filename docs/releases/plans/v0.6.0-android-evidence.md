## #6：窄屏编辑器布局（PRD §7.3）

375×812 视口下用 `vite preview` 真实构建复验（非模拟器，桌面浏览器窄视口）：
发现侧栏与主栏并排挤压导致底部四个导航页放不下的真实布局 bug，修复为
`AppShell` 的 `narrowFocus` 互斥显示后，四个真实状态（未选中/已选中/点返回/
桌面 1280px 三栏不回归）复验通过。详见
[requirements-traceability.md](../../requirements-traceability.md) PRD §7.3 行、

## #8：生命周期恢复（NFR-REL-02）

`Medium_Phone_API_35`：新建项目、勾选"启用 IPv6"（`StatusBar` 显示"保存中…"）、
按 HOME 切后台（触发 `visibilitychange`）、`adb shell am kill` 杀进程模拟低内存
回收（`ps` 确认进程消失）、重新拉起——重新打开该项目，IPv6 复选框仍为选中状态，
编辑未丢失。复验中顺带发现并修复一个真实 bug：`handleBottomNavigate('config')`
只重置了 `activeMobilePage`、没重置 `mainView`，导致从"关系"点回"配置"是静默
空操作（`BottomNav` 的高亮指示也卡住不动），只有真实点击才能发现——jsdom 测试
此前只覆盖了单向路径。详见 traceability.md NFR-REL-02 行。

## #9：存储压力降级（NFR-REL-05）

`Medium_Phone_API_35`：`adb shell dd if=/dev/zero of=/data/local/tmp/filler`
把设备 `/data` 分区从 28% 灌到 100%（可用空间压到约 1.2MB），全程重复编辑操作
——**应用不崩、编辑持续可用、UI 保持响应**，这是退出条件 6 的核心要求，多级压力
下反复确认成立。`StoragePressureNotice` 本身在这台设备上**未能**被触发显示：
根因是 `navigator.storage.estimate()` 报告的"可分配"配额比 `df` 看到的原始剩余
空间宽松（Storage Manager 把其它可回收缓存计入可分配），本应用实际写入量又很小
（几 KB YAML），三级降级信号需要的触发条件在这台设备上没被真实撞到——这是测试
方法本身的局限，不是代码缺陷：降级逻辑的另一半已经在 `packages/storage` 的注入式
失败 adapter 集成测试里被真实断言过。填充文件测试后已用 `rm` 清空，设备恢复
28% 基线。详见 traceability.md NFR-REL-05 行。

## #10：Ed25519 纯 JS 回退（ADR-028，退出条件 7）

`Medium_Phone_API_35`：先确认这台设备的 `crypto.subtle` 确实不支持 Ed25519
（`NotSupportedError: Algorithm: Unrecognized name`），再走一遍检查更新 → 安装 →
二次安装 → 回滚全链路（真实签名 Bundle，`tools/schema-cli` 同款签发流程生成）
——四步状态迁移全部通过 UI 文案确认成功。首次安装成功本身就是结论：原生后端已
确认不可用，能装上只能是 `NobleEd25519Verifier`（纯 JS）真的验证了签名。过程中
发现两个真实问题（均已记入 ADR-028）：`updater.ts` 的 `fileBaseUrl` 拼接约定不能带
末尾斜杠（测试夹具自身用法错误，非生产缺陷）；shell 内联环境变量经
bash→pnpm→vite 多层转发会破坏含花括号的 JSON 值（改用 Node 脚本直调 Vite
`build()` API 解决）。详见 traceability.md NFR-SEC-04 行、
[ADR-028](../../adr/ADR-028-pure-js-ed25519-backend.md)。

## #11：产品壳冷启动基线（NFR-PERF-01，退出条件 9）

`Medium_Phone_API_35`/`V14_API36_Large` 各 7 次冷启动采样（`am force-stop` 后
`am start -W`，进程级 `TotalTime` + 页面级 `MCS_FIRST_INTERACTIVE_MS` 双指标），
均远低于 2500ms 阈值。**API 29 补充验证（非计划要求，自主核实）**：安装产品壳
冷启动，`TotalTime: 919ms`，截图确认渲染的是 ADR-027 的"浏览器版本过旧 /
Browser Version Too Old"能力门文案（列出缺失的 `String.prototype.replaceAll`/
`Array.prototype.at`/`Object.hasOwn`），而非应用界面，与计划风险 R1 的预期完全
一致——截图见
[`v0.6.0-android-evidence-screenshots/api29-capability-gate.png`](./v0.6.0-android-evidence-screenshots/api29-capability-gate.png)。
完整数字、方法与和 spike 基线的对比见
[v0.6.0-perf-baseline.md](./v0.6.0-perf-baseline.md)。

## #13：接收其他应用分享（FR-AND-07，可选）

`Medium_Phone_API_35`，全程用 Chrome DevTools Protocol（`adb forward` 到
`webview_devtools_remote_<pid>`）直连 WebView，比坐标点击更可靠：

- **热启动**：项目已打开时 `adb shell am start -a android.intent.action.SEND
-t text/plain --es android.intent.extra.TEXT 'mode: global' -n
studio.mihomoconfig.app/.MainActivity`——命令行回显
  `Warning: ... delivered to currently running top-most instance` 确认走的是
  `singleTask` 的 `onNewIntent`，非新开进程；IndexedDB 内 `config.yaml` 读出确认
  变为 `mode: global`，页面显示"导入成功"。
- **冷启动**：`force-stop` 后直接用同样的分享 intent 拉起应用——先确认不崩溃、
  正确落在项目列表（`retainUntilConsumed` 分支不干扰正常挂载），再点开已有项目，
  `ImportPanel` 挂载瞬间"导入成功"提示出现，IndexedDB 内容变为分享的
  `mode: direct`——证明 Capacitor 的 `retainUntilConsumed` 事件补发机制（先于
  监听器到达的事件排队，监听器首次 `addListener` 时自动重放）在这条链路上真实
  生效，不只是读源码得出的推断。

详见 traceability.md FR-AND-07 行、[v0.6.0.md](./v0.6.0.md) #13 节的偏离说明
（`SafFilePlugin.kt` 只改 `handleOnNewIntent` 一处、不改 `MainActivity` 的取证
过程）。

## 已知缺口

- **FR-AND-01/02/03/04 的 SAF 交互式流程未验证**：v0.1.0 M0-5 spike 阶段做过完整
  的打开→编辑→另存→重新打开→分享手工点击验证（见
  [v0.1.0-android-evidence.md](./v0.1.0-android-evidence.md)），但那是 spike UI，
  不是产品壳；v0.6.0 #3 起的产品壳本身没有重新跑一遍同样的交互式点击验证——
  `assembleDebug`/启动冒烟证明产品壳能构建、能跑，不证明"点击系统选择器后文件
  真的能读写"。退出条件 1（打开→编辑→另存→重新打开）因此记 **Partial**，不是
  遗漏，是本版本收口时如实承认的缺口。
- **真机验证**：全部证据来自模拟器，真机复测不在本版本范围（决策 G1）。
- **GitHub Releases 发布验证**：#12 的本地部分（工作流文件、签名配置、CSP/清单
  决策）已完成，但真实推送、密钥配置与首次 CI/发布运行需要用户在 GitHub 网页侧
  完成（决策 G4）——按用户 2026-08-29 的决定，本次收口不等待这部分，退出条件 10
  如实记未完成，见 [v0.6.0.md](./v0.6.0.md) #12 节。
