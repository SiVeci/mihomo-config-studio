先决项 3 的核对细节（这是本轮唯一能靠读代码判定的一项）：

- **机制已在**：`verifyBundle` 的 `VerifyBundleOptions.trustedPublicKeys` 已经是
  `readonly Uint8Array[]`，且循环里"验过任何一把即通过"（[verify.ts:113](../../../packages/schema-registry/src/verify.ts)、
  `verify.ts:164-170`）。`verify.test.ts:248` 已有一条 `[current, next]` 轮换的正向用例。
- **值不在**：仓库里只有**单把** `BUILTIN_TRUST_ANCHOR_PUBLIC_KEY_HEX`（标量常量，非数组），
  且 [builtin.ts:17-28](../../../packages/schema-registry/src/builtin.ts) 明写它是
  "bootstrap 信任锚点，不是 ADR-010 §2/§3 描述的生产签名密钥"，其私钥
  "签完即丢弃，从未、也不在任何地方存储"，并要求
  "`tools/schema-cli` 必须在任何 Bundle 更新功能面向用户发布之前用真实密钥托管流程重新签发（v0.5.0）"。
- **没有"内置进构建产物"这一步**：没有任何构建期常量或配置把信任锚点数组喂给
  `apps/web`。目前只有 `builtin.test.ts` 在测试里用它。

结论：先决项 3 拆成两半——**数组形态 + 构建产物注入点**在 #0 自解（不需要真实密钥，
把现有单把 bootstrap 公钥放进 `[current, next]` 的第一格、第二格留空即可）；**生产公钥的
真实值**在你完成先决项 2 之后由 #14 填入并重签内置 Bundle。

**目标**：交付 `.github/workflows/schema-release.yml`，用你配好的 environment 与生产密钥
跑通一次完整签发，并验证审批确实拦得住未经批准的运行。

**你侧需要执行的步骤**（我不代做，也不接触私钥）

1. `Settings → Environments → New environment → schema-release`
2. Required reviewers：加你自己（1 人，按决策 F2）
3. Deployment branches：限定为 tag（`v*`），不含分支
4. 本地生成 Ed25519 密钥对，导出私钥为 PKCS#8 DER 的 base64（ADR-010 §2）
5. 把 base64 存为该 environment 的 secret `SCHEMA_SIGNING_KEY_B64`
6. 把对应公钥（raw 32 字节的 hex）告诉我 —— **只给公钥，不要给私钥**

**涉及文件**

- 新建 `.github/workflows/schema-release.yml`
- 新建 `docs/adr/ADR-024-single-maintainer-release-approval.md`

  重签内置 Bundle**

**实现要点**

- **ADR-010 §4 的四条逐条落实，且要能被指出在文件哪一行**：
  - 签名 job 独立，`needs:` 指向测试矩阵 job，只下载 artifact，**不重新构建**。
  - `permissions:` 最小化（签名 job 需要 `contents: write` 发 Release，仅此）。
  - 不引入任何第三方 action —— 只用 `actions/checkout`、`actions/setup-node`、
    `pnpm/action-setup`、`actions/upload-artifact`/`download-artifact`
    （与 `ci.yml` 已用的同一组，不新增）。
  - 禁 `pull_request_target`；触发条件只有 `push: tags: v*` 与 `workflow_dispatch`。
  - 私钥经 stdin 传入，**不得 `echo`，不得 `set -x`**。注意 `echo "$KEY" | cli` 与
    `printf '%s' "${{ secrets.X }}" | cli` 两种写法都违反这一条——前者字面就是 `echo`，
    后者把 secret 插值进 shell 命令行。正确形态是用 `env:` 把 secret 注入进程环境，
    由 Node 侧 `process.env` 读出后直接写进子进程 stdin，**shell 命令行里不出现密钥**。
    ADR-010 §4 已解释原因：GitHub 只对 secret 的精确字符串做日志遮罩，base64 一旦被换行、
    切分或重新编码就不再遮罩。这一步实现时逐字对照 ADR-010 §4 再定稿。
- **审批拦截的验收方式**：触发一次 `workflow_dispatch`，**不批准**，断言签名 job 停在
  waiting 状态且未产出任何签名产物；然后批准，断言产出。两次的 run URL 都记进证据。
- **生产密钥再签发**（`builtin.ts:22-28` 的要求）：拿到你给的公钥后，把
  `BUILTIN_TRUST_ANCHORS_HEX[0]` 换成它，用生产密钥重签内置 Bundle。这一步的签名动作
  **在工作流里发生，不在我本机发生**——我本机没有也不该有私钥。
- ADR-024 内容：偏离项（reviewers 1 而非 2）、原因（个人仓库无第二维护者）、补偿措施
  （tag-only deployment branches、禁 `pull_request_target`、零第三方 action、
  `permissions` 最小化）、回退条件（出现第二名维护者时立即恢复 ≥ 2）。
  **不改 ADR-010 原文。**
