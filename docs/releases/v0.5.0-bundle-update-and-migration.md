## 本版本要回答的问题

**Mihomo 更新之后，用户不装新应用能不能拿到新字段；而拿到新字段之后，他现有的配置会
不会被悄悄改变？**

这两问必须同时为"是"和"否"。前者是 ADR-002 的价值，后者是 ADR-004 的底线。

### 2. 迁移引擎（PRD §9.5、§12）

落点：`packages/migration`

- 迁移是**声明式**的（`migrations/*.json`），不含可执行代码。
- `MigrationPlan{ from, to, operations, warnings, lossy }`（PRD §10）。
- 升级预览必须展示：新增字段、废弃字段、默认值变化、迁移差异。
- **Lossy 标记默认取消**，要求显式确认，且先创建快照（NFR-REL-01）。
- 降级迁移必须预览；无法安全降级的字段保留在隔离区，**不能静默删除**。
- 缺失旧 Bundle 时项目进入只读保护并引导恢复（PRD §9.5 第 3 条）。

### 3. 发布工作流（ADR-010）

按 ADR-010 的四条约束实现：

- 签名 job 独立，只消费**已通过测试矩阵**的产物，不在签名 job 内重新构建。
- 签名 job 内不引入第三方 action，`permissions` 最小化，禁止 `pull_request_target`。
- 私钥经 stdin 传入 `schema-cli`；不得 `echo`，不得 `set -x`。
- 双人审核由 environment 的 required reviewers 实现，**不使用 repository secret**。

发布流程（PRD §8.9）：

```text
监控上游变化 → 生成差异报告和待审核 PR → 维护者更新 Schema/示例/迁移规则
  → Schema 静态检查 → YAML Golden Test → Mihomo 内核兼容测试矩阵
  → 人工审核 → 签名并发布 GitHub Release → 客户端校验、安装、可回滚
```

本版本打通「Schema 静态检查」之后的全部环节；「监控上游变化」是 FR-UPD-08，留到 v0.9.0。

### 4. CI 改造（必做）

`.github/workflows/ci.yml` 的 `no-network-egress` job 目前对 `packages/**` **全面禁止**
`fetch` / `XMLHttpRequest` / `WebSocket` / `sendBeacon`。Bundle 下载是第一个合法出网
路径，本版本必须把该检查从"全禁"改为**白名单**：

- 只允许 updater 模块出网。
- 另外断言其请求体不含配置内容——NFR-SEC-01 的实质是"不上传配置"，不是"不联网"。

改造前要先确认新检查仍能拦住原来的场景，否则这条守卫会退化成摆设。

## 风险

| 风险                                     | 影响                                  | 缓解                                                              |
| ---------------------------------------- | ------------------------------------- | ----------------------------------------------------------------- |
| 声明式迁移 DSL 表达不了某些结构变更      | 只能升级应用代码                      | ADR-002 已接受；记录被迫上升的案例作为 DSL 演进输入               |
| `no-network-egress` 白名单化后退化为摆设 | NFR-SEC-01 失去 CI 保护，属发布阻断项 | 改造时保留原有否定用例，新检查必须能拦住它们才允许合入            |
| 签名密钥泄露                             | 供应链攻击，PRD §18 列为低概率/高影响 | ADR-010 的 environment 审批 + 内置 `[current, next]` 支持快速轮换 |
| 迁移预览与实际迁移结果不一致             | 用户基于错误信息做决定                | 预览与执行走同一份 `MigrationPlan`，不允许两套代码路径            |
